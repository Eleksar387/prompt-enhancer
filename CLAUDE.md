# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

```bash
npm install      # first time only
npm run dev      # Vite (http://localhost:5173) + the history sidecar (http://localhost:8787), together
npm run build    # production build → dist/
npm run preview  # serve the production build locally (still proxies /api → the sidecar; run `npm run server` alongside)

npm run server   # just the history sidecar (server/index.mjs)
npm run dev:web  # just Vite
npm run import <file.json> [...]   # bulk-load history entries into the sidecar store
```

History, the vision-caption cache, and the project list persist in a **local Node sidecar** (`server/`), not the browser — see "State and persistence". Data lives at `~/.prompt-enhancer-data/` (`PE_DATA_DIR` to override).

## Backend configuration

The app supports four backends, configured via `.env` or the ⚙ Backend panel in the UI:

**Anthropic Claude API** (recommended — set in `.env`):
```
VITE_API_KEY=sk-ant-…
```
An `sk-ant-` key automatically sets the base URL to `https://api.anthropic.com/v1`. No other config needed.

**Grok API (xAI)**:
```
VITE_API_KEY=xai-…
```
An `xai-` key automatically sets the base URL to `https://api.x.ai/v1`. xAI's endpoint is OpenAI-compatible, so it needs no special browser headers — same `Authorization: Bearer <key>` path as Ollama. On an xAI backend the app can also **render** a finished prompt into a real image (`POST /images/generations` / `/images/edits`) or **video** (`POST /videos/generations` + polling) — see "Rendering a prompt into an image with Grok" and "…into a video with Grok" below.

**Checking your credit balance.** There is no in-app credit/budget readout, by design. The xAI *inference* API (`api.x.ai`, the `xai-` key) exposes no balance endpoint — `GET /v1/api-key` returns only key metadata, and the `usage` object on responses is token counts, not dollars. The prepaid balance lives only on xAI's separate **Management API** (`GET management-api.x.ai/v1/billing/teams/{teamId}/prepaid/balance`), which needs a distinct *management* key plus team ID and is not CORS-accessible from the browser. Check remaining credits in the xAI Console instead: **console.x.ai → Billing → API spend management**.

**OpenRouter**:
```
VITE_API_KEY=sk-or-…
```
An `sk-or-` key automatically sets the base URL to `https://openrouter.ai/api/v1`. OpenRouter is OpenAI-compatible too, so — like Grok — it needs no special browser headers, same `Authorization: Bearer <key>` path. Model ids are provider-prefixed (`anthropic/claude-sonnet-4-6`, `openai/gpt-4o`, `google/gemini-2.5-flash`, `x-ai/grok-4`, …); `pickWriter`/`pickVision` (`src/api.js`) match past that prefix (`(^|\/)grok-4` etc.), and `modelProvider()` (`src/history.js`) falls back to labeling any `/`-containing model id "OpenRouter" for the History filter, since an Ollama tag never contains a slash. OpenRouter has no image/video render endpoints in this app — the 🎨/🎬 Render buttons stay gated on `isGrok(cfg.base)` / a Gemini key, unaffected by this backend.

**Ollama (local)**: `OLLAMA_ORIGINS=*` must be set before starting Ollama. Default base URL is `http://localhost:11434/v1`.

**Gemini image rendering (optional, any backend)**: set a `cfg.geminiKey` (an `AIza…` key) in the ⚙ Backend panel — *not* via `.env`. This is decoupled from the backend/base URL: it only powers the 🎨 Render button (text-to-image + image editing via `generateImagesGemini`, model `cfg.geminiImageModel`, default `gemini-2.5-flash-image`). The key is sent only to `generativelanguage.googleapis.com` with an `x-goog-api-key` header (CORS-allow-listed there, so it works from the browser).

**One key per provider.** `cfg.apiKey` is the active key everything reads, but `ConfigBar` also keeps `cfg.apiKeys` (`{ anthropic, grok, openrouter, other }`, slot from `providerOf(cfg.base)` in `src/api.js`): a provider preset button stashes the current key under the provider being left and loads the saved one for the target, and typing in the key box writes both. Without this, switching presets left the previous provider's key in place and auth failed. Model lists (Writer/Vision in `App.jsx`, `AdaptPanel`) render through `src/components/ModelSelect.jsx`, a `<select>` with a substring filter box once there are more than 8 models.

`.env` values override localStorage on every page load. `VITE_API_BASE` can override the base URL explicitly. The `.env` file is gitignored.

### Anthropic API — how it works in the browser

Anthropic's API requires three headers for browser (CORS) access, sent automatically when `cfg.base` contains `anthropic.com`:
- `x-api-key: <key>`
- `anthropic-version: 2023-06-01`
- `anthropic-dangerous-direct-browser-access: true`

Grok (xAI), OpenRouter, and Ollama all use `Authorization: Bearer <key>`. The `authHeaders(cfg)` function in `api.js` selects the right set based on `isAnthropic(cfg.base)`. `isGrok(cfg.base)` (base contains `api.x.ai`) and `isOpenRouter(cfg.base)` (base contains `openrouter.ai`) are used for UI labeling/placeholders and to gate provider-specific request quirks/features. Do **not** add `format: 'json'` to requests when using Anthropic, Grok, or OpenRouter — it is Ollama-specific and is already gated in `callOllama` (all three cloud providers are excluded via the internal `isCloud` check).

### Two-stage pipeline

1. **Stage 1 — Vision** (`captionImages()` in App): sends image(s) to a vision model using a target-specific system prompt. Returns `{ text, stats }` (`stats = { fromCache, fresh }`). In `ref` mode it fires one call per reference image; every other mode makes a single call over 1–3 frames. The per-reference calls run through `mapWithConcurrency(refs, isCloud(cfg.base) ? refs.length : 1, …)` (`src/utils.js`) — **sequential against a local Ollama** (its parallel slots blend concurrent multimodal requests, so two references come back with a mixed description), fanned out for cloud providers. Same helper + gate in the scriptwriter's `captionRefImages`.
2. **Stage 2 — Writer** (`runWriter()` in App): sends the frame description + user controls to a writer model. The writer's system prompt encodes all domain rules for the selected generation target.

Text-only inputs skip stage 1. The "3 variants" mode runs stage 2 three times in parallel at temperatures `[0.3, 0.7, 1.0]`.

**Vision caption cache.** Every vision `callOllama` funnels through `cachedVision(content, system, stats)` inside `captionImages()`. The key is `visionCacheKey(effectiveVision, system, content)` (`src/utils.js`) — model id + `cyrb53` of the system prompt + each `content` block positionally (`cyrb53` of text blocks, `imageHash` = length-prefixed `cyrb53` of the base64 for image blocks). It auto-invalidates on any model / prompt / scene / role-`visionFocus` / frame-order / image-bytes change, and — because `restore()` fetches the entry's real image bytes back and the gallery re-hashes on pick — a reused image hits the same key. Two tiers: an L1 `captionMemRef` (`useRef(Map)`, session — **keep it**, it's what makes the now-networked L2 tolerable) and an L2 store in the sidecar (`captions/<enc-key>.json`, one file per key; `getCaption`/`putCaption` → `/api/captions/…`). Cache reads/writes are best-effort (`.catch(() => {})`); `putCaption` is `quiet` so a miss never raises the server-down banner. The old identity-keyed `visionCacheRef` / `refCaptionCacheRef` are gone; `enhance()` no longer has a pre-vision gate. The vision `<details>` summary shows "· N cached, M described" from `stats`; ⚙ Backend has a "Clear caption cache" button (`clearCaptions()` + `captionMemRef.current.clear()`).

**Editing the vision description.** The vision `<details>` body is a **textarea** bound to `caption` / `setCaption` (no longer read-only). `savedCaption` tracks the text as generated/restored (set alongside `setCaption` in `enhance()`, in `restore()`, cleared in `switchTarget` / `enhance` start); `caption !== savedCaption` drives an "· edited" tag and a **↻ Re-run writer with this description** button (`rerunFromCaption()` — rebuilds `stylePart`/`lengthPart` and calls `runWriter(caption, …)` directly, skipping a fresh vision pass, which saves a new history entry carrying the edited caption). A caption edit alongside existing results also sets `captionEdited`, which (like `resultsEdited`) surfaces the **💾 Save edited prompt to history** button. Each standard history card renders `<HistoryCaptionEditor value={h.caption} onSave={…} refImages={h.frameMode === 'ref' ? h.refImages : null}>` (`src/components/HistoryPanel.jsx`): a collapsible read view plus an inline textarea editor that persists via `updateHistoryEntry(h.id, { caption })` + `refreshHistory` (read view only, no Edit button, when the entry has no `id`). **This was the site of a bug that took three rounds to actually fix** ("editing one reference image's description overwrites/discards other images' descriptions"). A `ref`-mode entry's `caption` used to be the ONLY place a reference image's description lived — one shared text block, one `"Image N — role: …: <caption>"` line per reference. Editing it as one flat textarea (round 1) replaced every reference's description at once on save. Splicing just the matched line back in (round 2, `extractRefImageCaption`/`spliceRefImageCaption`, `src/adapt.js`) fixed clean data but fell back to the flat whole-block editor whenever a line failed to parse — the same bug again, one layer down (round 3 tightened the fallback to "show/edit only this line, empty if not found," which stopped the corruption but made `spliceRefImageCaption` on a non-matching line a **guaranteed silent no-op**: it re-ran the identical regex against the identical already-failing input, discarded the typed edit, and the UI still flashed "✓ saved" regardless). The actual fix (round 4) stops parsing the blob for saving at all: **a reference image's caption is now a real field on that image, `refImages[i].caption`**, written directly by App.jsx's `saveRefImageCaption(id, imageIndex, text)` — a plain array-index update (`h.refImages.map((im, i) => i === imageIndex ? {...im, caption: text} : im)`), never a regex match, so it can neither silently no-op nor touch a sibling index, and it works even on an entry whose old shared `caption` block is already corrupted by an earlier round (that block is simply never read or written through again for that image once it has its own `caption`). `extractRefImageCaption` (`src/adapt.js`) survives, read-only, purely as the *display* fallback for an image that hasn't been individually re-saved yet.

`HistoryCaptionEditor` renders one `RefImageCaptionRow` per reference (own thumbnail, own read/edit state, `onSaveIndexed(index0based, text)` → `actions.saveRefImageCaption(h.id, idx, text)`) whenever there's more than one reference image (`refImages.length > 1`, unconditionally — not gated on any line parsing, since there's nothing left to demote to); zero or one reference image falls back to the original flat single-textarea editor, where there's nothing to keep separate anyway. `HistoryImageGallery.jsx`'s per-thumbnail `ImageInfoPanel` follows the identical rule via its own `onSaveRefImageCaption` prop. Both save handlers now `try`/`catch` the call and show a distinct "✗ save failed" state on a thrown error, instead of the old `.catch(() => {})`-swallowed, always-"✓ saved" behavior (also removed from `saveCaption` itself) — a real network failure must be visible, not indistinguishable from success. `test/historyImageGallery.test.jsx` and `test/historyPanel.test.jsx` cover the full progression, including the case that matters most: an entry whose shared `caption` has **no** recognizable per-image structure left at all (round 1's actual damage) can still be repaired, image by image, going forward.

### Generation targets

Controlled by the `TARGETS` object in `constants.js`. Current targets: `ltx`, `ltx_guide` (LTX-2.3 video), `kling` (Kling AI video), `minimax_h3` (MiniMax H3 audio-video, 5 modes), `flux` (FLUX.dev image), `flux2klein` (FLUX.2 Klein image), `krea2turbo` (Krea 2 Turbo image), `grokimage` (Grok Image — natural-language prompt for xAI's `grok-imagine-image` model), `sdxl` (SDXL Danbooru-tag image), `threed` (3D-print miniature), `dramabox` (DramaBox TTS), `scriptwriter` (3-phase pipeline).

The **"Generate for" rail** in `App.jsx` renders these grouped and labelled via `TARGET_GROUPS` (`constants.js`) — an ordered `[{ label, ids }]` list (Script / Image / Video / External / TTS), each group a small header + top divider. `App.jsx`'s module-level `RAIL_GROUPS` appends a trailing "Other" group for any `TARGETS` id not listed, so a new target is never hidden. `TARGET_GROUPS` drives **only** the rail; `Object.values(TARGETS)` order still backs `ADAPT_TARGETS` and everything else.

Each target declares:
- `system` — writer system prompt
- `resolutions` — resolution preset array
- `show` — flags controlling which UI controls appear: `{ duration, camera, dialogue, frameMode, twoStage }`
- `visionPrompt` — system prompt passed to the vision model in stage 1 (image targets, plus `kling` — a video target whose vision prompt overrides `VISION_PROMPT_LTX_SINGLE` in single-image mode)
- `durations` / `durationHint` — (optional) per-target duration presets replacing the LTX `DURATION_OPTIONS`, and hint text under the picker (`kling` uses 5s/10s)
- `presetNote` — (optional) note shown under the resolution presets in `ImagePanel`, replacing the LTX/FLUX default text

The `scriptwriter` target has `type: 'scriptwriter'` and renders `<ScriptwriterPanel>` instead of the normal scene/image/generate UI.

### Rendering a prompt into an image with Grok (🎨 Render)

`generateImages(prompt, cfg, { n, aspectRatio, resolution, model, images })` in `src/api.js` — `POST {base}/images/generations`, or `{base}/images/edits` when `images` (reference images, `[{ base64, mediaType }]`) is passed → **image-to-image**. xAI's OpenAI-ish JSON API, `response_format: 'b64_json'`, plain bearer auth via the now-exported `authHeaders`. One ref → `image: { url: <data URI>, type: 'image_url' }`; 2–5 refs → `images: [...]` (prompt can address them as `<IMAGE_0>` …). Returns `[{ b64, url, mediaType, revisedPrompt }]`; `mediaType` prefers the response's `mime_type`, else sniffs the base64 header (`mediaTypeFromB64`). Retries once without `aspect_ratio`/`resolution` if the model rejects them. `DEFAULT_CFG.imageModel` (`'grok-imagine-image-2.0'`) is the default model, editable in a **grok-only** field in ⚙ Backend.

**Gemini path.** `generateImagesGemini(prompt, { key, model, aspectRatio, images, signal })` — `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent` with an `x-goog-api-key` header (CORS-allow-listed, so browser-callable). One code path for text-to-image and editing: the prompt plus any `images` become `contents[0].parts` (`{ text }` + `{ inline_data: { mime_type, data } }` each). `generationConfig: { responseModalities: ['IMAGE'], imageConfig: { aspectRatio } }` (retries once without `imageConfig` if rejected). Parses every `candidates[0].content.parts[].inlineData.data` into the **same** `[{ b64, url, mediaType, revisedPrompt }]` shape as `generateImages`, so the rest of the render pipeline is provider-agnostic. Gemini returns one image per call, so `renderImage` fans out `imageCount` parallel calls (`Promise.allSettled`). Default model `cfg.geminiImageModel` (`'gemini-2.5-flash-image'`). No resolution/2K knob and no ⬆ Upscale button on the Gemini path (Grok-only).

Every generated prompt result gets a **🎨 Render** button (`renderImage(idx)` in `App.jsx`) — shown when `canRender` (`grokRenderOn = isGrok(cfg.base)` **or** `geminiRenderOn = !!cfg.geminiKey`), on *any* target. `imgProvider` = whichever is available, or `renderProvider` (a `'grok'|'gemini'` session toggle shown in the strip) when both are. It passes `currentImages()` (the currently-loaded input image(s), carrying `mediaType`) as `images`, so with a reference/frame image loaded the button reads **🎨 Render from image** and both providers run image-to-image (Grok `/images/edits`, Gemini `inline_data` parts); otherwise plain text-to-image. Above the results a compact "🎨 Render" strip exposes `imageAspect` (from `GROK_IMAGE_RESOLUTIONS[].ar`; Gemini accepts the same ratio strings), `imageCount` (1–4), the `imgProvider === 'grok'`-only `imageResolution` (`1k`/`2k`), and the `via` provider select, plus a green "image-to-image: N references loaded" hint. Rendered images show inline under the result textarea with a `⬇ Save image` link and a collapsible "revised prompt". The 🎬 Grok video sub-row and ⬆ Upscale button stay gated on `isGrok(cfg.base)`.

Rendered images persist onto the **existing** history entry: `renderImage` calls `persistOutputs(idx, { images })`, which rebuilds `outputs` from `resultsRef.current` (a live mirror of `results`) and patches it via `updateHistoryEntry(id, patch)` (`src/db.js` → `PATCH /api/history/:id`; the sidecar splits any base64 in the patch into content-addressed blobs). `lastSavedEntryIdRef` tracks which entry the live results were last saved as (set by `saveHistory` — which now takes a `trackForRender` flag so an Adapt-panel save doesn't hijack it — and by `restore()`). `restore()` rehydrates `o.images` into the results; history cards render `outputs[*].images` as thumbnails; `exportBundle` adds them to the ZIP as `render-<i>-<k>.<ext>`.

**⬆ Upscale to 2K** — each rendered image gets an `upscaleImage(i, k)` button that re-runs it through `generateImages(r.text, cfg, { images: [{ base64, mediaType }], resolution: '2k', aspectRatio: imageAspect })` (the `/images/edits` img2img path) and replaces `results[i].images[k]` (marked `upscaled: true`). xAI has no true upscale endpoint — this is an edit pass, so fine detail shifts slightly; the UI says so. Per-button state in `upStatus` keyed `"i-k"`.

### Rendering a prompt into a video with Grok (🎬 Render video)

`generateVideo(prompt, cfg, { model, duration, resolution, aspectRatio, audio, image, onProgress, signal, pollMs, timeoutMs })` in `src/api.js` — `POST {base}/videos/generations` → `{ request_id }`, then polls `GET {base}/videos/{request_id}` every 4 s (10-min cap) until `status` is `done` / `failed` / `expired`, calling `onProgress(status, pct)` between polls. Body: `{ model, prompt, duration (1–15, clamped), resolution, aspect_ratio, generate_audio, image: { url } }`. With an input image loaded it's image-to-video (first frame). Retries once without the optional params if the model rejects them (mirrors `generateImages`). Resolves `{ url, duration, model }`. **Video is a temporary URL on `vidgen.x.ai` — there is no base64 response option.** `DEFAULT_CFG.videoModel` (`'grok-imagine-video-1.5'`) editable in the grok-only ⚙ Backend block. DEV-only `window.__peVideoPollMs` overrides the poll interval for the headless driver.

`renderVideo(idx)` in `App.jsx` mirrors `renderImage`: gated `r.text && isGrok(cfg.base)`, one `AbortController` per result index in `videoAbortRef` (aborted by `switchTarget` / `switchMode` / `enhance` / unmount / a re-click). After it gets the URL it **best-effort** `fetch(url) → blob() → base64` and stores `results[i].video = { url, b64?, mediaType: 'video/mp4', duration }`; a cross-origin failure leaves it URL-only (still playable in `<video>`; the UI then shows "Open video ↗" + an expiry note instead of "⬇ Save video"). Second row of the render-options strip: `videoDuration` (1–15, kept in step with the target's duration via a `useEffect`), `videoResolution` (`480p`/`720p`/`1080p`, default `720p`), `videoAspect` (= image aspects minus 21:9), `videoAudio` (default on). Persists onto `outputs[i].video` via `persistOutputs` (same `lastSavedEntryIdRef` path); the sidecar stores captured MP4 bytes as a blob (`o.video.url` → `/api/blob/…`, `download` offered) and leaves a URL-only video pointing at the (likely-expired) `vidgen.x.ai` link; `restore()` rehydrates `o.video`; history cards show a `🎬 video` link; `exportBundle` adds `render-<i>.mp4` when bytes were captured.

### Scriptwriter pipeline (`scriptwriter` target)

`ScriptwriterPanel.jsx` runs three sequential LLM calls with user-review gates between each. It is **MiniMax H3-first** — `promptTarget` defaults to `'minimax_h3'` (`DEFAULT_PROMPT_TARGET`) and is chosen on the script-review screen (phase `script`) so Phase 2 can specialise; `'ltx'` keeps the original workflow unchanged.

**Layout.** `App.jsx`'s top-level grid is the same three-column `360px minmax(0,900px) minmax(420px,760px)` (left rail / compose / output) for every target, `scriptwriter` included, and every grid child now carries an explicit `gridColumn` (`'1'`/`'2'`/`'3'`) rather than relying on child order. Unlike every other target, `<ScriptwriterPanel>` itself is the direct grid child in place of a single column-2 wrapper — its top-level return is a fragment of two halves, each its own `gridColumn`-tagged `<div>`: a **compose half** (`gridColumn:'2'`) — `HistoryImageGallery`, `ScriptwriterRefImages`, `ScriptwriterVoiceRefs`, and the Phase-1 idea/genre form, i.e. everything before "✦ Write Script" — and a **results half** (`gridColumn:'3'`) — the phase stepper, the error banner, and whichever review screen is current (script bible, Director's Cut, final prompts). CSS grid's sparse auto-placement then stacks the results half directly above the right column's `<HistoryPanel>` (both `gridColumn:'3'`, neither given an explicit row), so "generate → result → history" reads top-to-bottom in one column exactly as it does for every other target, instead of the Scriptwriter's results sitting in the compose column with History in a separate one. The left rail (Generate for / Project / models / ⚙ Backend) is unconditional and identical across targets; only the `!scriptwriterMode` guards on the right column's empty-state placeholder and the `<QueuePanel>` (the Scriptwriter renders its own filtered copy inside its Full Auto tab, see below) differ per target.

**Inspecting the actual prompts.** The Scriptwriter has no Admin-mode pause of its own (that hook lives only in `App.jsx`'s single-shot pipeline, via `useAdminReview`, and never runs when the Scriptwriter tab is open). In a DEV build (`npm run dev`), each phase instead stashes its exact `{ system, user }` request on `window` right before sending it, readable from the browser console: `window.__peLastPhase1Message`, `window.__peLastPhase2Message`, and `window.__peLastH3Messages` (an array, one `{ shot, mode, system, msg }` per clip — `msg` is the user message). This is the way to check, e.g., whether a scene the script clearly wrote (a flashback) survived into the Director's Cut, or into a specific clip's prompt — the stash happens every run, so re-running the phase in question and re-reading the same global is enough.

1. **Phase 1 — Script + bible** (`SYSTEM_PROMPT_SCRIPTWRITER`): story idea → JSON `{ title, logline, format_note, look, language, soundscape, music, characters[{ id, name, role_in_story, appearance, wardrobe, voice }], locations[{ id, name, description }], scenes[{ id, title, location_id, setting, characters[ids], description, dialogues[], emotional_turn, sound_mood }] }`. `look` / `language` / `soundscape` / `music` are film-level; `characters`/`locations` are the canon bible; per-scene `sound_mood` overrides the film soundscape/music. Shown as editable cast/location cards + scene cards. The prompt is tuned for the **micro-film format** (~45 s–3 min): a "THE FORMAT" rule block up top — one premise / one turn / one ending, latest-possible entry point, show the consequence not the process, prefer a single location, and narrow an over-large idea to its smallest self-contained moment rather than compressing the whole arc; dialogue is pushed to near zero and only one scene normally carries a real `emotional_turn`. Scene count (1–5, default **1**) is a **maximum, not an exact target** — the writer rule says "at most N", and a single continuous action in one place is instructed to stay ONE scene even when the cap is higher; the input screen carries a one-line note about the format plus the ceiling framing, and the stepper is labelled "Scenes (max)". **`format_note`** is the writer's own flag: `""` when the idea fits, else one sentence naming what was left out — `normalizeScript` coerces it to a trimmed string, the script screen shows it as a dismissible amber banner (`dismissFormatNote` → `setScript` + `persistState(…, scriptOverride)`), and it persists/restores on the `script` object. The input screen (with the `idea` textarea) only renders in `phase` `input`/`scripting` — once the script exists, that screen is gone, and with it any visible trace of what was actually submitted. The Script screen shows a read-only **Story Idea (as submitted)** block above Film Title for this reason: `idea` for a Guided run, or (when `autoJob` is live or the restored entry has `fullAuto` set) the Full Auto hint / "AI invented freely" fallback instead of the long `buildAutoIdea` boilerplate. Reachable from any later phase via "← Back to Script", same as the rest of the bible.
2. **Phase 2 — Director's cut**: `promptTarget`-dependent. `'ltx'` → `SYSTEM_PROMPT_DIRECTOR` (unchanged). `'minimax_h3'` → **`SYSTEM_PROMPT_DIRECTOR_H3`** — thinks in *clips* (one H3 generation = one emotional/action unit) and adds `shot_type` (performance/action/establishing/insert), `characters[ids]`, `location_id`, `eyeline`, `primary_beat` (physical, never an emotion label), `dialogue[]`. Rules encode the `h3-storyboard` skill (≤2 facial beats/clip or split, cut-as-performance, camera-from-eyeline, dialogue-shots-carry-only-that-line, insert clip per emotional turn, tail-settle margin, H3-valid durations) and require `characters` to be exact bible ids. It also emits **`reference_images`** per clip — 1-based numbers into the numbered "Reference images" block — for the references that actually help that clip (a face reference only when the face is visible, not under a helmet / blanket / turned away; wardrobe/prop only where on screen; location for clips in that place). `runPhase2` first captions any undescribed refs (so the Director sees the full list), then `resolveRefSelection(reference_images, capd)` maps each clip's picks to `shot.refs` (the pin the chips + Phase 3 already consume); an absent field leaves the clip on the auto default. Both keep the JSON key `shots`; the UI says "Clip" for H3.
3. **Phase 3 — clip prompts**: `'ltx'` → `buildLtxGuideSystemPrompt('single')` (unchanged, plain text). `'minimax_h3'` → `SYSTEM_PROMPT_MINIMAX_H3` via `buildH3ShotMessage(shot, ratio, refsList)`, one parallel `callOllama` per clip. `buildH3ShotMessage` emits **`MODE: Ref2VA`** whenever the film has **any** captioned reference (`shotRefs(shot, scene)` → if `shot.refs` is an array (a set the user pinned on the Director's-Cut screen — reference *keys*, `refKey(im)` = `im.hash`), exactly those captioned refs; otherwise `autoShotRefs()` — *all* captioned refs, the main-app Ref2VA model, narrowing face/wardrobe refs per clip only when 2+ identity refs exist; environment/style/prop stay global). The role-tagged block is **byte-compatible with `App.jsx`'s `captionImages()` ref-mode output** (`Image N — role: <label>, preservation: <label> (<marker>): <caption>` + `Requested use of this reference: plays <name>` / `the "<name>" environment`). Only with **zero** captioned references does it fall to **`MODE: T2VA`** with the bible's appearance/wardrobe/location text inlined. Both modes add `Aspect ratio:` / `Primary language:` / `Film look:` and film/scene `overall_soundscape` + `non_diegetic_music` lines. `runPhase3` first auto-captions any linked-but-undescribed reference, and (DEV only) stashes the built messages on `window.__peLastH3Messages`. Each returned clip prompt runs through **`normalizeH3Prompt(text, isRef)`** (module-level) — strips a wrapping ```` ``` ```` fence and re-attaches a dropped first field label (`integrated_multimodal_description:` for T2VA, `subject_definitions:` for Ref2VA; the writer model omits it inconsistently). Applied in `runPhase3`, `regeneratePrompt`, and the `finalPrompts` `useState` initialiser (repairs older restored entries).

**Aspect ratio.** One `aspectRatio` state (id into `MINIMAX_H3_RESOLUTIONS`, default `land169` = 16:9), used as a **target-agnostic** aspect list — only its orientation / ratio token matters, not the H3 pixel dims. Pickable on the **input screen** (next to genre / scenes) and on the Script screen's Output-Model card (both targets now — was H3-only; Pacing stays H3-only); locked from `dircut` on. Persisted in `basePayload` as `aspectRatio` (back-compat: `restore()` reads `aspectRatio ?? h3Ratio`). Two `constants.js` helpers key off a resolution entry's `note` and emit only the clean token (`16:9`, `9:16`) — never the raw `note` (its `768P/2K` tail is H3-specific): `aspectSceneHint(res)` (one line, empty for 16:9) is appended as `Delivery format:` in `runPhase1` + `regenerateScene`; `aspectFramingHint(res)` (1–2 sentences, empty for 16:9) is appended as `Framing for delivery:` in `runPhase2` + `regenerateShot` (**unconditional** — LTX Director too) and prepended as an `Aspect ratio:` + framing block in the LTX branch of `buildShotPromptMsg` (Phase 3 LTX previously dropped the `ratio` arg entirely). `generateFramePrompt` adds a `Target aspect ratio:` line. H3 Phase 3 already carried `Aspect ratio:` via `buildH3ShotMessage` — unchanged. Matching acknowledgement rules were added to `SYSTEM_PROMPT_SCRIPTWRITER`, `SYSTEM_PROMPT_DIRECTOR`, `SYSTEM_PROMPT_DIRECTOR_H3`, and `LTX_GUIDE_INTRO`. Portrait/`generatePortraitPrompt` is deliberately left ratio-free (standardised identity plate).

**Id normalisation.** LLMs drop / rename the `c1`/`l1` ids the ref-attachment path depends on. `normalizeScript(data)` assigns `c1..cN`/`l1..lN` and resolves every `scenes[].characters` / `scenes[].location_id` (names or ids) to those; `normalizeDirectorsCut(data, script)` does the same for `shots[].characters` / `location_id` / `scene_id`. Both run in `runPhase1`/`runPhase2` **and** the `script`/`directorsCut` `useState` initialisers, so restored / older / model-broken entries self-repair on load. A `useEffect([script])` **backfills a link target** for any reference that has a `linkType` but no `linkId` — by name match (note/caption) or the sole entry of that kind — so a half-linked ref still shows on its cast/location card and narrows correctly; `refForEntity` / `refBelongsTo` apply the same lenient rule. The Director's-Cut screen (H3) shows a **reference-status banner** — amber "no described references → all T2VA", or green "✓ All N clips generate as Ref2VA".

**Per-item AI re-write.** Each of the three review screens can re-run the AI for one item in place. On the **Script screen** (`phase === 'script'`) each scene card has a **✦ Rewrite** button (`regenerateScene(si)`) — re-runs `SYSTEM_PROMPT_SCRIPTWRITER` (temp 0.85) with the whole current script + bible as context, asks for a fresh version of that one scene (JSON `{scenes:[<one>]}`), merges it over the old scene keeping its `id`, and re-runs `normalizeScript` on the result so cast/location links stay resolved. On the **Director's-Cut screen** (`phase === 'dircut'`) each clip/shot card has a **✦ Rewrite** button (`regenerateShot(si)`) — re-runs the Director (`SYSTEM_PROMPT_DIRECTOR_H3` / `SYSTEM_PROMPT_DIRECTOR`, temp 0.85) with the whole current shot list as context, asking for a fresh take on that one shot only (JSON `{shots:[<one>]}`), then splices it back keeping `shot_number` / `scene_id` / `scene_title` and the parallel `framePrompts` slot. On the **Video-Prompts screen** (`phase === 'done'`) each prompt has a **✦ Rewrite** button (`regeneratePrompt(idx)`) — re-runs phase 3 for that shot (`buildShotPromptMsg`, temp 0.85) and replaces `finalPrompts[idx]` in place. All re-save the session (`persistState` gained a `cutOverride` param; `regenerateScene` / `regeneratePrompt` commit directly). `sceneBusy` / `shotBusy` / `promptBusy` hold the index in flight and disable the sibling rewrite buttons (and the "→ Director's Cut" button) meanwhile.

**Insert / remove clips** (Director's-Cut screen, `phase === 'dircut'`, H3 + LTX). Each clip card has a danger-tinted **✕** (`removeShot(si)` — drops the clip, disabled at 1 clip left) beside its ✦ Rewrite; a slim dashed **"+ Insert clip (AI writes it)"** bar sits between every card and at both ends (`insertShot(atIndex)`). Insert appends a `blankShot(neighbor, isH3, script)` (inherits scene / location / cast / look from the adjacent clip), then immediately calls `regenerateShot(atIndex, { cut, bridge: true })` — the `bridge` flag (also triggered by an empty `primary_beat` / `visual_action`) switches the Director prompt to "write a NEW clip between clip N and N+1". `renumberShots` re-sequences `shot_number`; the index-parallel `framePrompts` array is spliced in lockstep; `picker` / `comfyFrame` / `attach` (all keyed `"<shotIdx>-<frameKey>"`) are reset. `normalizeDirectorsCut` is not re-run — `blankShot` already sets valid ids.

**Merge clips** (Director's-Cut screen, H3 only). Repeated live testing showed prompt wording alone (`PACING_LINE`, then the `Pacing: TIGHT` insert/establishing exceptions below) does not reliably reduce clip count — confirmed against both a non-reasoning and a reasoning-capable writer model, both still over-splitting a single continuous locomotion run (sit → stand → step off a ledge) into separate clips. The fix is deterministic instead of another prompt edit: `isMergeEligible(a, b)` is a pure, code-side check — both `shot_type` in `{'establishing', 'action'}` (H3's own "does not count toward beat density" categories), same `scene_id`/`location_id`/`characters`, neither carries `dialogue`, combined `duration` ≤15s (H3's clip cap). This is deliberately conservative — it will under-merge a locomotion beat the model mislabeled `performance`, but never risks merging two real facial/emotional beats, which would violate the one rule in `h3-storyboard` with direct empirical (PSNR) backing. `mergeShotPair(shots, i, refs)` is the one LLM call this ever makes, shared by both triggers below — same message-building pattern as `regenerateShot`'s "bridge" call, but scoped to the narrow, tractable question "merge these two already-known-compatible clips into one," never the open question "how many clips should this scene have" that kept failing. Two triggers: a manual **"⇄ Merge"** button next to ✦ Rewrite (hidden on the last clip) calling `mergeShots(si)` — a mismatched pair (fails `isMergeEligible`) gets a `window.confirm` nudge rather than a hard block, so manual override still works; and an automatic pass inside `runPhase2`, right before `setDirectorsCut`, that greedily merges every eligible adjacent pair (not advancing the index after a merge, so 3+ compatible clips chain into one) whenever `autoActive && pacing === 'tight'` — i.e. Full Auto only, since it never reaches this screen for a manual click. A failed merge call skips that pair rather than aborting the job — **unless the model refused the request outright** (see "Content refusals" below), in which case the whole job stops instead.

**Content refusals stop the whole script, not just one call.** A writer-model response that declines the request outright ("I can't help with this request…") comes back as prose, not JSON — `parseJSON`'s catch already fails it, but several call sites (the automatic merge pass, Full Auto's parallel per-clip Phase 3) previously treated that failure as a transient hiccup and kept going to the next call, which is wrong for a refusal specifically: it means the *script's own content* (usually a reference image, sometimes the hint) is the problem, not the model having a bad day, so retrying elsewhere in the same script is pointless and just repeats the same call. `looksLikeRefusal(text)` (module-level, `ScriptwriterPanel.jsx`) matches a short list of first-person refusal openers against short (<2000 char) non-JSON text; `parseJSON` tags a matching error `isRefusal: true` with the actual refusal text as the message. The automatic merge loop rethrows on `isRefusal` instead of skipping to the next pair, so it lands in `runPhase2`'s normal catch (`setError` + revert to `script`) exactly like any other Phase 2 failure. `runPhase3`'s per-clip calls still fire in parallel — a refusal on one clip can't un-send another's already-in-flight request — but the result is no longer allowed to reach `phase: 'done'`/report success: if any clip's response matches `looksLikeRefusal`, the run discards the batch, surfaces which clip and why in `error`, and reverts to `dircut` instead of persisting a "finished" film with a silently-broken clip. Manual per-item rewrites (`regenerateScene`/`regenerateShot`/`mergeShots`) already just `setError` and stop on any failure, refusal included — no auto-continue there to begin with; `regeneratePrompt` (Phase 3's per-clip rewrite) is the one exception, since its output is the same plain, non-JSON text as the batch Phase 3 call — it now runs the same `looksLikeRefusal(raw)` check before saving/committing, where previously a refusal would have been silently stored and persisted as if it were a real clip prompt. `captionRefImages` (vision, not writer) gets the same treatment for a different reason: a vision-model refusal resolves normally (`callOllama` doesn't throw), so without a check its refusal prose would be stored as that reference's `caption` and then folded into every downstream Phase 1/2/3 message by `assembleRefBlock` — poisoning the rest of the run with content the vision model itself already flagged. A refusal caption is now excluded from the successful set and the function throws `isRefusal: true`; all four call sites (`runPhase1`, `runPhase2`, `runPhase3`, `regeneratePrompt`) stop on it instead of their prior best-effort "keep going with what we have."

**Per-clip reference pinning** (Director's-Cut **and** Video-Prompts screens, `phase === 'dircut'` or `'done'`, H3 only). The "References attached to this clip" block is interactive on both screens: every captioned reference renders as a toggle chip — ticked ones (the effective `shotRefs()` set) are attached, struck-through ones are excluded. Clicking a chip calls `toggleShotRef(si, im)`, which seeds an explicit set from the current effective refs and adds/removes `refKey(im)` (= `im.hash`), storing it as `shot.refs` (an array; `[]` = deliberately none). While `shot.refs` is an array `shotRefs()` returns exactly those captioned refs; otherwise it falls back to `autoShotRefs()` (the old "all captioned, narrow on 2+ identity refs" default). **"reset to auto"** deletes `shot.refs` (`resetShotRefs(si)`). The pins are **Director-seeded** — Phase 2 (and a `regenerateShot` that returns `reference_images`) fills `shot.refs` via `resolveRefSelection`, so re-running the Director re-picks them; the user then hand-adjusts. A pinned set survives `regenerateShot` (unless it re-picks) and persists through `persistState`; `normalizeDirectorsCut` passes `refs` through untouched. This is the fix for a face/wardrobe/prop reference being sent on clips where it does not belong (the shirt under a still-closed coat; a face reference on a clip where the face is under a helmet or blanket).

**Adding a reference after Phase 3 has run.** `ScriptwriterRefImages`, `ScriptwriterVoiceRefs`, and the "♻ Reuse image from history" gallery (all in the compose column) stay editable through phase `'done'` — locked only during `'prompting'` itself, while Phase 3's batch of parallel writer calls is in flight — so a reference image or voice-timbre reference can be added (uploaded, or an image pulled from history) and described without navigating back to Director's Cut. A **new image reference must be described (captioned) before it can be attached to any clip** — an uncaptioned upload doesn't appear as a chip yet; click "👁 Describe images" in the panel, or add a per-image note and use "Describe" on it, first. On the Video-Prompts screen the per-clip chip row (H3 only, and only once at least one reference is captioned — otherwise it just shows the static "No described references yet" line, not clickable) is editable the same way it is on Director's Cut: pinning a new reference onto a clip there does **not** retroactively rewrite that clip's already-generated prompt text (an amber note says so) — the user still clicks that clip's own **✦ Rewrite** (`regeneratePrompt`) to fold the change in, which already commits the current `refImages` via `persistState`/`commitHistory` alongside the new prompt text. **Per-clip voice-reference pinning.** H3's audio input takes **up to two** separate voice-timbre samples per clip (`ref_audio_0` / `ref_audio_1`, `<Audio 1>` / `<Audio 2>` in the schema — not one; `SYSTEM_PROMPT_MINIMAX_H3`'s Ref2VA rule and `buildH3ShotMessage`'s `Audio N —` lines both loop over up to two). `voicesForShot(shot, scene, dialogues)` (module: `ScriptwriterPanel.jsx`) resolves them for a clip and only applies to one that actually carries dialogue: an explicit pin (`shot.voiceCharacterIds`, an array of bible character ids, `[]` = deliberately none) wins outright; otherwise auto-resolution tries, in order, the `"Name:"` prefix on each dialogue line, then every cast member who has a linked sample, then any unlinked ("default voice") samples — and whenever a step would need to guess which two of three-or-more candidates to send, it sends none instead. The Director's-Cut / Video-Prompts clip card has a **"Voice references for this clip"** chip row (H3 only, editable in `dircut` and `done` the same way as the image-reference chips) — click up to 2 to pin an exact set, or **"reset to auto"** to drop the pin; `toggleShotVoice(si, characterId)` / `resetShotVoice(si)` mirror `toggleShotRef`/`resetShotRefs`. A pinned set survives `regenerateShot` (explicitly carried over, since the Director's JSON has no field for it) and a `mergeShotPair` merge (unioned, capped at 2). On the Video-Prompts screen, **"🔊 Attach/Update voice (…)"** next to ✦ Rewrite runs the same low-temperature `VOICE_PATCH_SYSTEM` patch call as the single-voice case, now naming one or two `Audio N:` references to attach/update/remove — it adds, updates, or drops `<Audio N>` lines to match the given set exactly (removing any not given, renumbering contiguously) rather than assuming there is always exactly one.

This is a generalization of a previously single-audio design (the code and system-prompt rule originally assumed exactly one `<Audio 1>` per clip) to match the real MiniMax H3 ComfyUI node, which exposes two audio-reference inputs (`ref_audio_0` / `ref_audio_1`) — user-confirmed 2026-09-14 (`ref_audio_1` exists and works). `.claude/skills/h3-storyboard/SKILL.md` §九 and its `SOURCES.md` still document and verify only `ref_audio_0` in detail (pitch/range/accent numbers from an actual generation) — the exact prompt-text pattern for a SECOND `<Audio 2>` reference and how cleanly H3 keeps two simultaneous voice-timbre references separated per speaker is extrapolated from the verified single-audio pattern, not independently measured the same way. Update `SOURCES.md` with a real two-voice test (ideally with per-speaker pitch/range numbers, mirroring the existing `ref_audio_0` entry) when one is run.

The main (non-Scriptwriter) pipeline's `MinimaxRefPanel.jsx` `ref` mode carries the same two-slot `refAudios` array (see "MiniMax H3 target notes" below) — a separate, parallel generalization of what was originally a single-`refAudio` field there too; the two are independent user-tested confirmations of the same underlying two-audio-input capability (user-reported 2026-09-14), not one shared code path (the Scriptwriter's `voiceRefs` and per-clip `voicesForShot`/`voiceCharacterIds` are unrelated data structures from `MinimaxRefPanel`'s `refAudios`, since one generation there produces one MiniMax H3 call directly rather than a per-clip breakdown).

**Free step navigation.** The phase stepper dots and explicit **"← Back to Script" / "← Back to Director's Cut"** buttons (on the Director's-Cut and Video-Prompts screens) let the user jump between any finished step at will — `navigateTo(target)` is pure navigation, never re-runs the LLM (`stepReachable(target)` gates on `script` / `directorsCut` / `finalPrompts` existing; `navBusy()` blocks during a generation). `stepIdx` now tracks the visible screen (`input`/`scripting`/`script`/`directing` → 0, `dircut` → 1, else 2). **`persistState` always stores every artifact that exists** regardless of the current `phase` (it gained `phaseOverride` + `promptsOverride` params) — so a history record carries the whole path and `restore()` drops the user back on `initialState.phase` with script + cut + prompts + frames all rehydrated and the stepper live. `insertShot`/`removeShot` now splice `finalPrompts` in lockstep too (`emptyPromptEntry` / `renumberPrompts`) for the case where the user stepped back to `dircut` after generating. The forward buttons that *do* re-run (`runPhase2` "↻ Re-run Director's Cut", `runPhase3` "↻ Re-generate all Prompts") `window.confirm` before discarding downstream work.

**Folded clip/shot and prompt cards.** Both long lists — the Director's-Cut clip/shot cards and the Video-Prompts cards — start folded (an index-keyed `expandedShots` / `expandedPrompts` `Set`, transient view state, not persisted) and open individually via a click on the card's own header (a dedicated toggle `<button>` wrapping just the chevron/title/scene-title/badges, kept separate from the header's action-button group so clicking ✦ Rewrite / ⇄ Merge / ✕ / Copy doesn't also toggle the fold). A folded clip card shows a one-line summary (primary beat/visual action + duration) in place of its full field set; a folded prompt card shows a truncated first line of the generated text. Each list also gets an Expand all / Collapse all pair once it has more than one card. A card auto-expands when something happens to it: `regenerateShot`/`mergeShots`/`insertShot`'s bridge call add their index to `expandedShots`, `regeneratePrompt` adds its index to `expandedPrompts` up front (so "Generating…" is visible), and a prompt card additionally force-expands whenever `p.loading || p.error` regardless of the fold state — a refused/failed clip must never be hidden behind a folded header. `insertShot`/`removeShot`/`mergeShots` re-key both `Set`s across the same splice they already do to `directorsCut.shots`/`finalPrompts` (`shiftExpandedForInsert`/`Remove`/`Merge`) so a fold state stays attached to the right card after the list shifts.

**Pacing control** (`pacing`: `tight` / `standard` / `loose`, default `standard` in Guided mode — `tight` for Full Auto, see below — persisted in `basePayload`). A button row on the Script screen inside the Output-Model card, H3 only (sits under the now-shared Aspect Ratio picker — see "Aspect ratio" above). `runPhase2` appends `PACING_LINE[pacing]` to the Phase-2 user message (H3 branch), and `SYSTEM_PROMPT_DIRECTOR_H3` rule 1 now says "prefer the fewest clips that respect the beat-density limit … a 3-scene film is typically 8–14 clips, not 20+ … if the user message carries a 'Pacing:' line, follow it" — the fix for the H3 director over-splitting. Two further rules are conditional on pacing directly in their own text (not just the injected line, since a standalone pacing line was previously outvoted by unconditional mandates): the per-turn insert-clip convention and the establishing-clip convention both relax under `Pacing: TIGHT` (skip/fold them unless the scene genuinely needs one). The beat-density limit itself (≤2–3 facial beats/clip) is **never** relaxed by pacing at any level — it's the one rule in `h3-storyboard` with direct empirical (PSNR) verification; the insert/establishing conventions are the tool's own editorial codification of the skill's general cutaway-editing advice and were the safe place to soften.

**Full Auto mode.** A **Guided / Full Auto** toggle at the top of the input screen (`autoMode` state, UI-only). Guided is the pipeline described above, unchanged. Full Auto shows only the reference-image uploader (still the same `ScriptwriterRefImages`, cap 6 — the "one or more images" become one shared reference set for a single film), a Genre picker, an optional one-line **Story hint** text field, and a **Pacing** picker (own `autoPacing` state, default `'tight'` — deliberately separate from Guided mode's `pacing` state, which stays default `'standard'` since those users already see it on the Script screen; Full Auto never reaches that screen, so pacing needed its own visible control here) — no `idea` textarea, no scene-count/aspect-ratio/target pickers (those stay hidden on their existing defaults: max 1 scene, 16:9, `minimax_h3`). Its **"+ Add to Queue (Full Auto)"** button (disabled until at least one reference image is added) calls `onQueueAutoJob({ refImages: serializeRefImages(refImages), genre, hint, pacing: autoPacing })` — a prop from `App.jsx`'s `addScriptwriterAutoJob`, which queues a `{ kind: 'scriptwriter-auto', snapshot: {...} }` item through the same `addQueueItem`/`server/queueStore.mjs` used by the main pipeline's queue (that store is shape-agnostic, so no backend change was needed for the different snapshot shape). The Full Auto tab also renders its own `<QueuePanel>`, fed via a `queueProps` prop from `App.jsx` and filtered to `kind === 'scriptwriter-auto'` — there is still just **one** shared queue; `App.jsx`'s main `<QueuePanel>` (hidden while the Scriptwriter tab is open) shows the same items when not on that tab, since `QueueCard` now branches on `item.kind` to render either shape.

`basePayload` stamps every saved entry with `fullAuto: !!autoJob` and `fullAutoHint: autoJob?.hint || ''` — a Full Auto entry's `idea` field is a fixed ~180-char boilerplate instruction (`buildAutoIdea`'s `AUTO_IDEA_BASE`) with the user's hint appended after it, so the History card's old 80-char `idea` preview always showed the boilerplate, never the hint. `App.jsx`'s history card now shows `h.fullAutoHint` (or "AI invented freely" when empty) instead of the truncated `h.idea` whenever `h.fullAuto` is set, plus a "🎬 Full Auto" label next to the model name.

Running a queued Full Auto job (`App.jsx`'s `runScriptwriterQueueItem`, dispatched by `runAnyQueueItem` alongside the main pipeline's `runQueueItem`) switches `target` to `'scriptwriter'` and forces a fresh `<ScriptwriterPanel key={scriptwriterKey}>` mount carrying the job as its `autoJob` prop (mirrors the main queue's target-switching precedent — `applyQueueItemToWorkspace` already does the same for a main-pipeline item). On mount, `ScriptwriterPanel` seeds its own state from `autoJob` — `idea` is synthesized (`buildAutoIdea`: a fixed "invent the whole premise from the images and genre" instruction, plus the optional hint) since `runPhase1` still requires a non-empty `idea` and is otherwise untouched — via `flushSync` (same reason as `enhanceRef`/`runQueueItem`: without it, the kickoff call would run against the previous render's stale closure) and immediately calls `runPhase1`. A phase-watcher `useEffect` then auto-advances Phase 1 → 2 → 3 with no review clicks (`phase2Ref`/`phase3Ref`, reassigned every render like `enhanceRef`), guarded by `!error` so a phase's own failure-recovery `setPhase(...)` doesn't re-trigger the next step; reaching `phase === 'done'` or an unrecovered `error` on `phase === 'input'` / `'script'` / `'dircut'` calls `onAutoJobDone({ ok, error? })`, which resolves `runScriptwriterQueueItem`'s pending promise (delete-on-success / keep-with-error-on-failure, same as the main queue) — the `'script'`/`'dircut'` cases cover a Phase 2/3 failure (a bad-JSON error, or a content refusal, see "Content refusals" above) reverting the phase with `error` set; before this the watcher only recognized a Phase 1 failure (`phase === 'input'`), so a later phase's failure left `autoActive` stuck true with the job's promise never resolved. A per-clip error in Phase 3 that ISN'T a refusal still doesn't stop the run — `runPhase3` has no top-level catch for those, so it reaches `done` and reports `ok: true` with that one clip broken; the result is a completely normal, restorable Scriptwriter history entry (saved via the same `onSaveHistory`/`persistState` path every phase already uses), and the failed clip is fixable there via ✦ Rewrite exactly as in a manual run. A refusal is the one failure mode that does NOT get this treatment — see above.

**Export ZIP** (`exportBundle`, "⬇ Export ZIP" next to "Copy all" on the done screen): bundles `prompts/clip-NN.txt` (each with its clip header — number, scene, duration, Ref2VA/T2VA, which references to load), `prompts.md` (all clips), `references/<linkId>-<name>.<ext>` + `references.md` (portraits and uploads, role/preservation/caption), `frames/shot-NN-<key>.<ext>` (attached LTX frame images), `script.json`, `directors-cut.json`, `manifest.json`, and a human `README.md` (title/logline/look/language/soundscape/music, cast, locations). JSZip, `zip.generateAsync` → object-URL anchor download. The downloaded filename is `<Title>-video-<model>-<date>.zip` — scriptwriter output is always `video` (both `minimax_h3` and `ltx` are `TARGETS[...].type === 'video'`, even when the same zip also carries per-frame image prompts as a bonus deliverable) and `<model>` is `minimax` for H3, `ltx` otherwise.

**`manifest.json`** is the machine-readable counterpart to the human-facing files above — built for automation that needs to consume the export without parsing prose (see `comfyui-prompt-enhancer-bridge/` below). Per clip: `promptFile` + `promptText` (the raw generated text, no header), `mode` (Ref2VA/T2VA), `durationSec`, `outputName`, and `references` (`[{file, role, preserve}]`) **in the exact order** that clip's prompt text numbers them (`Image 1 —`, `Image 2 —`, …) — this matters because H3 reads Ref2VA reference images positionally, so a wrong order silently attaches the wrong identity to a clip. Built via `clipRefsFor(i)` (already used for the human clip header — same `shotRefs()` call, same `refImages` array, so the order matches by construction) and a `refFileByKey` map recorded while writing `references/` in the same pass, so a manifest entry can never point at a file the zip doesn't actually contain.

**Main pipeline's Export ZIP** (`App.jsx`'s own `exportBundle`, next to Copy all on any target's result) uses the same `<Title>-<video|image>-<model>-<date>.zip` shape, generalized for a pipeline with no dedicated title field: `titleSlug(scene)` (lowercased, punctuation stripped, first 8 words, hyphen-joined) stands in for the title and is simply omitted when there's no scene text to draw one from (MiniMax H3 ref mode, a pure vision-only run); the category is `TARGETS[target].type` (`video`/`image`/`text`) and `modelSlug(target)` is the target id with `minimax_h3` shortened to `minimax` (its `_h3` suffix reads as an internal detail, not the model name) and any other underscore turned into a hyphen (`ltx_guide` → `ltx-guide`).

Phases 1 & 2 use `callOllama(..., { format: 'json' })` (Ollama JSON mode; ignored on Anthropic). Phase 3 does not.

**Reference images + cast portraits.** `ScriptwriterRefImages.jsx` lets the user attach up to 6 reference images, each with a free-text `note`, a **link type** (`REF_LINK_TYPES`: character / wardrobe / location / style / prop) that auto-picks a default H3 **role** (`MINIMAX_H3_REF_ROLES`) + **preservation** (`MINIMAX_H3_PRESERVE_OPTIONS`) — both overridable in a "role / strength" row — and, once the bible exists, a **link target** (which named character or location). Fields persist via `serializeRefImages` (`{ base64, mediaType, fileName, note, caption, linkType, linkId, role, preserve, generated, hash }`) / `rehydrateRefImage`. `captionRefImages()` describes each image via `callOllama(visModel, …, VISION_PROMPT_MINIMAX_H3_REF + role.visionFocus, …)` when the image is typed (a wardrobe ref → garment only, etc.), else the general `VISION_PROMPT_SCRIPTWRITER`. Captions are editable. The panel is editable through phase `dircut` (read-only in `prompting`/`done`). A **"♻ Reuse image from history"** block (`HistoryImageGallery`) sits at the top of the panel on every phase before `prompting` — picking a thumbnail runs `addRefFromHistory` (dedupes on `hash`/bytes, fuzzy-links via `guessRefLink`, keeps a carried `ref`-slot caption or else `captionRefImages`), so a portrait or reference from a past run is one click away.

Default preservation per link type (`REF_LINK_TYPES`): character → `subject_identity` + **`exact`** (lock the face), location → `environment` + **`guide`** (transfer the room), wardrobe → `strong`, style → `inspiration`, prop → `strong` — matching a hand-tuned reference example. An uploaded reference auto-links to a bible entry by fuzzy-matching its note/filename against character then location names (`guessRefLink`, applied in `addRefFiles` / `updateRefNote`).

Each cast/location card has an embedded **portrait generator + on-card Upload/Describe** (`renderPortrait(key)` / `portraitDraft`): **Upload** (`uploadPortrait` → `fileToRef`) drops a photo straight in and sets `linkType`/`linkId`/`role`/`preserve` + captions it; **Generate** writes a still-image prompt from the bible entry + film `look` (`FRAME_SYSTEM[target]`, default `zimage`), `→ ComfyUI` (`sendPortraitToComfy` → `sendShot`) + `＋ Attach render` (`attachPortraitImage`) pull the render back; **Describe** (`describeEntityRef`) captions an existing-but-undescribed ref. All routes produce a `generated`/uploaded `refImages` entry linked to that entry, auto-captioned via `captionRefImages({ imgs })`. `refForEntity` / `removeEntityRef` manage it; mid-phase re-save via `persistState(undefined, refsOverride)`.

`assembleRefBlock(refImages, heading, script)` folds captioned images into the user message of Phase 1 (`REF_HEADING_CANON`), Phase 2 for LTX (`REF_HEADING_DIRECTOR`), each Phase 3 LTX shot (`REF_HEADING_SHOT`), and the LTX frame-image prompts (`REF_HEADING_LITE`; `sdxl` skipped) — lines read `Image N (Character — "MARA" — note: …): <caption>`. The H3 Phase 3 path does **not** use `assembleRefBlock`; it builds a real Ref2VA block (see Phase 3 above). `SYSTEM_PROMPT_SCRIPTWRITER` and `SYSTEM_PROMPT_DIRECTOR` each carry a rule acknowledging the folded block; `SYSTEM_PROMPT_DIRECTOR_H3` acknowledges the bible + reference block. `guardHistorySize` drops `refImages[].base64` (generated portraits and uploads alike) **before** frame-image bytes. `entrySearchText` indexes bible names + notes + captions; `HistoryImageGallery.collectImages` walks `refImages` so portraits are reusable in other targets.

**Frame Image Prompts (LTX target only).** Rendered on the Director's-Cut screen only when `promptTarget !== 'minimax_h3'` (for H3, each clip card instead shows a "References attached to this clip" chip row + the resulting `MODE: Ref2VA` / `MODE: T2VA`). Each shot card also generates per-frame still-image prompts (`first`/`mid`/`last`, target `flux`/`flux2klein`/`zimage`/`sdxl` — `FRAME_TARGETS`/`FRAME_SYSTEM` in `ScriptwriterPanel.jsx` map each to a writer system prompt) held in `framePrompts` (array parallel to `directorsCut.shots`; `{ frames: { <key>: { target, text, image, loading, error } } }`). Each generated prompt has a `→ ComfyUI` button (`sendFrameToComfy` → `sendShot` to the bridge slot) and a `＋ Attach image` button that opens an inline picker of ComfyUI's recent outputs (`fetchComfyOutputs` = `GET /history`, newest first) — clicking a thumbnail runs `fetchComfyImageBlob` (`GET /view`) → `shrinkToJpeg` (≤1536px JPEG, shared helper in `src/utils.js`, also used by `ImagePanel`) → `frames[k].image = { b64, mediaType, width, height, source, ts }`, shown inline with Replace/Download/Remove. `framePrompts` is serialized (`serializeFramePrompts`, drops `loading`/`error`) into the phase-2/phase-3 `onSaveHistory` payloads and re-saved mid-phase via `persistState()` when an image is attached/removed; `guardHistorySize` nulls the largest attached images if the record would exceed ~12 MB (surfaced as `historyNote`). `restore()` rehydrates via `rehydrateFrameEntry`. Scriptwriter history cards show the attached frame images as 72px thumbnails. Needs ComfyUI started with `--enable-cors-header` (the `<img>` thumbnails load without it, but the attach fetch and `/history` do not).

### `comfyui-prompt-enhancer-bridge/` — auto-run an export ZIP in ComfyUI

A separate, standalone ComfyUI custom node pack (own top-level folder, not part of the Vite app — the user copies it into `ComfyUI/custom_nodes/`) for running a Scriptwriter export end-to-end on a ComfyUI instance this app's browser can't reach over the network (e.g. a locked-down work machine — the zip is the only thing that needs to cross that boundary; nothing here talks back to the Prompt Enhancer app). It reads the export's `manifest.json` (see above) rather than parsing `prompts/*.txt` prose.

Three custom node classes (`nodes.py`) give the pack a rename-proof way to find "which node is which" in the user's own template workflow — matched by `class_type` (stable, present in ComfyUI's `/prompt` API payload) rather than node titles (rename-sensitive, live in a separate JSON): `PEClipPrompt` (`STRING` out — the whole clip's `promptText`), `PEClipImage` (`index` widget + `IMAGE` out, loaded from an absolute staged path rather than `LoadImage`'s validated `input/`-folder dropdown), and `PEClipDuration` (`FLOAT` out, seconds — optional; a template with none just keeps its own fixed length for every clip, flagged as a non-blocking notice in the review panel). The user wires these into their own MiniMax/H3-calling workflow once; the pack is generic prompt/image/duration patch-and-requeue plumbing, not H3-specific.

`__init__.py` registers those nodes plus one aiohttp route (`POST /prompt_enhancer/run_film`, guarded so importing the package without a running ComfyUI server — e.g. under test — no-ops instead of erroring) that accepts the raw zip bytes, hands off to `staging.py` (stdlib-only: `zipfile`/`shutil`/`json`/`os`, no `pip install` needed) to extract into `ComfyUI/input/prompt_enhancer_runs/<run-id>/` and rewrite every manifest reference to its staged absolute path, and returns the manifest to the browser.

`web/patch.js` is the pure graph-patching logic (deliberately split out of `web/pe_bridge.js` so it has no dependency on ComfyUI's `app`/`api` modules and is unit-testable with plain Node — `tests/test_patch.mjs`): clones the currently-loaded workflow (`app.graphToPrompt().output`) once per clip, sets every `PEClipPrompt`/`PEClipImage`/`PEClipDuration` node, and — only when there's exactly one `filename_prefix`-bearing node in the whole graph (ambiguous otherwise, so left untouched rather than guessed) — best-effort stamps it with the clip's output name. `web/pe_bridge.js` is the UI shell — a "📦 Load Film" button / zip drag-and-drop, a review panel (per clip: prompt preview, which staged file fills which slot, duration; a hard-stop if no `PEClipPrompt` node exists, a warning if a clip needs more `PEClipImage` slots than the template has, a non-blocking notice if there's no `PEClipDuration` node) with a **Run** button before anything is submitted, then `api.queuePrompt` per clip (passing the real captured `workflow`, not an empty one, so a finished clip's provenance/graph stays recoverable from ComfyUI's own history) with `/history` polling for progress. The panel docks to a corner rather than a full-screen modal (a modal blocked the canvas and any preview node's live output during a run) and auto-collapses to a one-line header status once a run starts. Both the button and the panel (by its header) are drag-repositionable via `makeDraggable()` — a fixed default spot collided with the Queue button on at least one real ComfyUI theme — with position remembered in `localStorage` (`pe-bridge-btn-pos`/`pe-bridge-panel-pos`) across reloads; a drag-vs-click guard (`wasDragged()`, a short timer after a real drag's `mouseup`) stops the native click that still fires on mouseup from also triggering the handle's own click action (opening the file picker / toggling collapse).

`tests/test_staging.py` (Python, stdlib only) and `tests/test_patch.mjs` (Node) are offline unit tests against synthetic fixtures — this pack was built without access to a running ComfyUI, so neither exercises a real queue/execution; see the pack's own `README.md`.

### Admin mode

A toggle in the header. When on: after stage 1 completes, `enhance()` pauses and populates two editable textareas (system prompt + user message) instead of calling the writer. `sendToWriter()` fires stage 2 from whatever is in the textareas. `pendingSnapshotRef` (useRef) holds the generation snapshot between phases.

### State and persistence

All UI state lives in `useState` hooks inside `App`. Two things persist to `localStorage`:
- **Backend config** (`ollama-enhancer-config`): base URL, API key, temperature.
- **ComfyUI copy config** (`prompt-enhancer-comfy-config`): just the ComfyUI server URL (default `http://127.0.0.1:8188`) used by the "⇪ Copy to ComfyUI input" button — see below.

Plus one-shot migration guard flags (`idb-migrated-v1`) and, historically, `localStorage['gen-history']` / `prompt-enhancer-projects` — both now migrated into the sidecar (see below).

`VITE_API_KEY` / `VITE_API_BASE` from `.env` override localStorage values on every page load.

**Generation history + caption cache + project list live in a local sidecar server, NOT the browser.** The browser IndexedDB store this replaced was silently wiped twice (origin drift — Vite had no `strictPort`, so a busy 5173 moved the app to 5174 and a *different, empty* IndexedDB; possibly also quota eviction of the multi-MB inline blobs). Now:

- **`server/`** — a zero-dependency Node sidecar (`node:http` + `node:fs`, ESM, default port **8787**, `PORT` / `PE_API_PORT` env). Vite proxies `/api` → it (`vite.config.js`, both `server` and `preview`); `npm run dev` runs both via `scripts/dev.mjs` (kill one → both die). `npm run server` / `npm run dev:web` run them separately.
- **Data dir** — `PE_DATA_DIR`, default `~/.prompt-enhancer-data/` (**outside the repo** so `git clean -fdx` can't wipe it). Layout: `entries/<id>.json` (pretty-printed; blob fields replaced by `{ blobRef, hash, bytesKey, mediaType }`), `blobs/<hash>` + `<hash>.type` (content-addressed, `hash = imageHash(base64)` — `server/hash.mjs` is a **byte-identical copy** of `cyrb53`/`imageHash` from `src/utils.js`; keep them in sync), `captions/<enc-key>.json` (one file per `visionCacheKey`), `projects.json`, `trash/<ISO-ts>/…` (soft delete/clear — `DELETE` and `POST /api/history/clear` *move* files here, never `unlink`), `tmp/` (atomic-write scratch — every write is `writeFile`→`fsync`→`rename`).
- **Endpoints** (`server/index.mjs`): `GET /api/history` (metadata array — blob nodes stripped to `{ blobRef, hash, mediaType, url }`, **no bytes**), `GET /api/history/:id[?inline=1]` (one entry; `inline` rehydrates real base64), `PUT`/`PATCH`/`DELETE /api/history/:id`, `POST /api/history/clear`, `GET`/`PUT /api/projects`, `GET`/`PUT /api/captions/:key`, `POST /api/captions/clear`, `GET /api/image-meta` + `PATCH /api/image-meta/:hash` (per-image role/descriptions; `captions` merges per role key server-side), `POST /api/import` (`{entries, captions}`, idempotent on `id`), `GET /api/export?inline=1`, `GET /api/blob/:hash` (raw bytes, `immutable` cache, ETag), `GET /api/health` (`{ ok, entries }`). In-memory index of stored entries built at boot (`server/store.mjs`), updated on every write; disk is the source of truth.
- **`src/db.js`** — same call surface over `fetch('/api/…')`. `getAllHistory` was **renamed `listHistory()`** (metadata only) and there's a new `getHistoryEntry(id, { inline })`; a module-level `setWriteErrorHandler` drives App's persistent "History-Server nicht erreichbar" banner (`historyDown` state) on any write/health failure. `loadProjects` is now async. `putCaption` writes `quiet` (an L2-cache miss must not raise the banner).
- **`src/db.idb.js`** — the old IndexedDB file, unwired, kept only so `migrateFromIndexedDB()` (one-shot, guarded by `idb-migrated-v1`, leaves the IndexedDB intact as a cold backup) can read the previous store. `migrateFromLocalStorage()` still handles the older capped-10 `gen-history` format. The recovered `prompt-enhancer-history-RECOVERED*.json` files were imported via `npm run import <file.json>` (`server/import.mjs` — never the browser: 34 MB body).
- **Bulk import CLI:** `npm run import <file.json> [...]` reads a JSON array (or `{entries, captions}`) straight into the store. **Backup:** `tar czf backup-$(date +%F).tgz -C ~ .prompt-enhancer-data` or `GET /api/export?inline=1`.

**Perf:** history rows carry no image bytes, so `refreshHistory()` after every mutation (the Scriptwriter fires it ~15×/session) reloads KB not MB; history-card and gallery thumbnails are `<img src="/api/blob/…">` (browser-cached, out of the JS heap) instead of `data:` URIs; content-addressing dedupes an image reused across entries to one file on disk. The Scriptwriter's `persistState` is **debounced ~600 ms** (trailing, flushed on unmount — safe because every save is a full snapshot under one stable `sessionId`); its old `guardHistorySize` 12 MB record cap (which *nulled* `refImages[].base64` to fit) is **gone** — no size cap, blobs live on disk.

`updateHistoryEntry(id, patch)` (→ `PATCH`) is still the read-modify-write the 🎨/🎬 render features use to attach `outputs[i].images` / `outputs[i].video`; the server splits any base64 in the patch into blobs. `restore()` is now `async` — it fetches `getHistoryEntry(h.id, { inline: true })` so the image panels / ComfyUI copy / ZIP export get real bytes; the ScriptwriterPanel gets the same rehydrated entry as `initialState`. Dragging/clicking an image in `HistoryImageGallery` carries only its blob URL; `resolveDragImage()` (`src/imageDrag.js`, via `blobUrlToBase64` in `src/utils.js`) fetches the bytes on drop/pick.

**Project folders.** Each history entry carries an optional `project` field (a name string, or `null` = Unfiled). The **Project** picker (under "Generate for") sets `activeProject`, which `saveHistory` / `saveScriptHistory` stamp onto every new entry; the scriptwriter re-saves the same `id` across its three phases, so `saveScriptHistory` preserves a project the user reassigned in the meantime rather than resetting it. Existing entries are reassigned in place via a per-card `<select>` (`entryProjectSelect` → `assignEntryProject` → `setHistoryEntryProject(id, project)`, a read-modify-write so it works on entries saved before the field existed). `allProjects` (a `useMemo`) is the union of the persisted list and every name referenced by an entry, so a project stays selectable even if its localStorage record is lost.

**History filters.** A filter bar (shown when `history.length > 1`) narrows `visibleHistory` by five independent, AND-combined criteria: a **free-text search** (`histSearch` — a `type=search` box, always the first control in the bar; whitespace-split into terms that must *all* be substring-matched), **project** (`historyFilter`: `all` / `unfiled` / a name), **target** (`histTargetFilter`: `all` / a target id — `entryTargetId(h)` returns `'scriptwriter'` for scriptwriter-type entries, `h.target` otherwise), **writer model** (`histModelFilter`: `all` / an exact model string — options are `modelFilterLabel(m)` = `"<provider> · <model>"` where `modelProvider` classifies a model string as Claude / Grok / Ollama), and **image inputs** (`histImageFilter`: `all` / `with` / `without` — `entryHasImages(h)` is true if any of `firstImg` / `midImg` / `lastImg` / a non-empty `refImages` / a `vision` model is present). The search haystack is `entrySearchText(h)` (module-level, lowercased, no image bytes): scene, vision caption, generated output text/labels, negative, style, project, model, target label — or, for scriptwriter entries, the idea, script title, `JSON.stringify`'d scenes/shots, and final-prompt text. It's memoised per entry in `histSearchIndex` (rebuilt only when `history` changes). Each select only renders when the history holds more than one distinct value for it; the search box always renders. `histFiltersActive` gates the **Reset** button and switches the header count to `visible/total`. All helper functions (`entryTargetId`, `entryTargetLabel`, `entryHasImages`, `entrySearchText`, `modelProvider`, `modelFilterLabel`) are module-level pure functions near `buildVariants`. `renameProject` / `deleteProject` bulk-update affected entries (delete → entries become Unfiled); `restore()` also sets `activeProject` to the restored entry's project. `importHistory` registers any project names it sees in the imported entries. Entries predating this feature simply have no `project` key and read as Unfiled. `migrateFromLocalStorage()` + `migrateFromIndexedDB()` one-time-migrate any pre-existing `localStorage` `gen-history` and browser-IndexedDB data into the sidecar on first load. Each entry's snapshot includes any input image(s) used — full `{ base64, mediaType, fileName, hash }` data (plus `role`/`preserve`/`note` for MiniMax H3 reference images, and a separate `refAudio` for the H3 voice-timbre reference), not just a filename — so `restore()` repopulates the live image panels (`firstImg`/`midImg`/`lastImg`/`refImages`) directly from history, making a restored entry immediately usable again (regenerate, ZIP export, "Copy to ComfyUI input"). `restore()` also rehydrates the generated output(s) — it maps `h.outputs` back into the `results` array (`loading:false`, `usage:null`) so the restored prompt text reappears in the editable results textareas (`editResult` on change), not just the settings; a multi-variant run restores all three. It closes the History panel (`setHistoryOpen(false)`) like the scriptwriter path. Hand-edits to the results textareas can be persisted as a **new** history entry: each result object carries `saved` (the text as generated/restored); when any `r.text !== r.saved` (and not an error/empty), `resultsEdited` is true and a **💾 Save edited prompt to history** button appears next to Export ZIP. `saveResultsEdit()` builds a snapshot from the current workspace via `buildSnapshot(frameDescription, hasImg, count)` (extracted from `runWriter` — the single source of the history-snapshot shape, also used for fresh generations), calls `saveHistory`, re-stamps `saved` on every result, and flashes "✓ Saved to history" (`savedEditFlash`, 1.8s). The original entry is never modified. The snapshot also stores `caption` (the assembled vision description) so a restored/history-selected image-based entry can be re-targeted by `AdaptPanel` without re-running vision, and adapt-produced entries carry `adaptedFrom: { target, frameMode, ts }`. Entries saved before this existed only have a filename string; `restore()` and the history-list thumbnail rendering both check for object-shaped image data and fall back to the old label-only behavior for those, so no migration was needed.

### Reusing images from history

`HistoryImageGallery` (rendered just above the image panels whenever `showImage` — every target except `dramabox` — and also at the top of `ScriptwriterPanel`, below the phase stepper, on every phase before `prompting`; there `onPick` = `addRefFromHistory`, which adds the image as a Scriptwriter reference, fuzzy-linked to the bible by note/filename, keeping any carried-over caption/role or else describing it on the spot) walks every history entry and collects the unique images — both the input frames (`firstImg`/`midImg`/`lastImg` + each `refImages[]`) and any **Grok-rendered output images** (`outputs[].images[]`, which store their bytes under `b64` not `base64`, so `consider()` reads `im.base64 || im.b64`). For a `ref`-slot image a per-image `im.caption` (the Scriptwriter stores one per reference) wins over the entry-level `h.caption`; `onPick` forwards that caption/role/note only for `ref`-slot picks. `collectImages(history)` returns `{ images, stats }`: images are deduped via a `Map` keyed on a **cheap composite** (`fileName|len|head64|tail64`) rather than the full multi-MB base64, sorted newest-first; `stats` (`{entries, rawFields, objWithBase64, collected}`) drives a DEV-only diagnostic — `console.debug` every history change plus a `console.warn` if `collected === 0 && objWithBase64 > 0` (a real traversal/gate bug). Rendered entries carry a `render` badge (`🎨` / `🎨 2K` for an upscaled one) and a synthesised `grok-render.<ext>` filename; they have no `hash` (downstream re-hashes via `imageHash` when needed). **Legacy history entries that stored only a filename string** never pass the base64 gate (same gate the history-list thumbnails use) and are silently skipped — no explanatory UI. The section **auto-expands the first time it has ≥1 image** (session-sticky via a ref once the user toggles it); when a history exists but has no byte-backed images it still shows the collapsed `(0)` toggle with a one-line stats-aware empty state. The visible grid is capped at `CAP = 60` (with a "showing 60 of N" note), thumbnails are `loading="lazy" decoding="async"`, and the grid scrolls internally (`maxHeight: 340`).

Each collected image also carries the **vision description** from the newest generation that used it: `consider()` threads `caption` (`h.caption`, or `im.revisedPrompt` for renders) + `captionScope` (`single` / `multi` (first-last / first-mid-last share one caption — see below) / `ref` / `ref-item` / `render`) + `entryId` (`h.id`). Every tile has a small **i** badge (top-right); clicking it opens `<ImageInfoPanel>` below the grid — reads the description, and (when `onSaveCaption` is wired and the source entry has an `id`, renders excluded) an **✎ Edit description** → textarea → Save that persists via `App`'s `onSaveCaption={(entryId, text) => updateHistoryEntry(entryId, { caption: text }).then(refreshHistory)}`. `multi`'s frames share one description because the vision model itself wrote it that way — ONE call sees all the frames together and returns one interconnected "FIRST FRAME: … LAST FRAME: … CHANGE: …" narrative (`captionImages()`'s `firstlast`/`firstmidlast` branches, `src/App.jsx`), not separable per-frame text — so editing there still rewrites the whole shared block, unavoidably.

**`ref` mode is different and used to have a real bug here**: each reference image's caption comes from its OWN independent vision call, but the main (non-Scriptwriter) pipeline only ever stored the *concatenated* result as one shared `h.caption` block (`captionImages()`'s `ref` branch) — unlike the Scriptwriter, which already keeps one `caption` per reference image. Editing "one image's description" in the info panel used to show — and Save used to overwrite — that WHOLE block. After a few rounds of trying to safely parse/splice that block instead (see "Editing the vision description" above for the full history), the fix stopped depending on the block at all: saving started writing straight to `refImages[i].caption` (a plain array-index update, never a regex match) — later **generalized to a role-keyed map**, see "🤖 Describe with AI" below, which is what actually saves it now. `consider()` resolves the image's own-role text through `resolveRefCaption(im, ownRoleKey, ctx.caption, refImageIndex)` (`src/adapt.js`) — priority: the structural `captions` map → the legacy flat `im.caption` (read-only from here on) → `extractRefImageCaption(ctx.caption, refImageIndex)` (the even-older shared-block extraction, also read-only) → empty. `ImageInfoPanel.save()` and `HistoryPanel.jsx`'s `RefImageCaptionRow` both read through this SAME resolver (not their own copies), so a save made from either surface is never shown as stale/reverted by the other. A thrown save error shows "✗ save failed" instead of a false "✓ saved" (no `.catch(() => {})` swallow anywhere in this path).

**🤖 Describe with AI — re-running vision on one stored reference image, under ANY role, on demand.** `ImageInfoPanel` (`HistoryImageGallery.jsx`'s "♻ Reuse image from history" gallery, **only** — not the finished-generation history card, see below) shows one row per role the image has been described under — its own assigned role always first (even if empty), then any other role with stored text — each with `roleIcon(roleId)` (🧑/👕/📦/📍/🎨/🤸, ❓ when the role is unset/unrecognized; `MINIMAX_H3_REF_ROLES[].icon`, `src/constants.js`), the role label, the stored text, **✎ Edit**, and **🤖 Describe/Re-describe with AI**. Below the rows, a compact icon row (`MINIMAX_H3_REF_ROLES` entries not already shown) lets the SAME image be described under a role it doesn't have yet — e.g. a person photo already described as `subject_identity` can also be described as `pose_composition` (body position/framing only, a genuinely different `visionFocus`), and both texts are kept side by side. Clicking an icon runs the description immediately — no separate confirm step. Everything is wired to `App.jsx`'s `describeRefImage(entryId, imageIndex, roleId)` (`historyActionsRef.current`, exposed only through `galleryActions` — deliberately left out of the `historyActions` bundle `<HistoryPanel>` receives, see next paragraph); `roleId` defaults to the image's own assigned role when omitted (`MINIMAX_H3_REF_ROLES.find(r => r.id === (roleId || im.role)) || MINIMAX_H3_REF_ROLES[0]`), so its `visionFocus`/`visionSystem` picks the right vision-model framing per role. It fetches that one image's bytes on demand (`blobUrlToBase64(im.url)`, `src/utils.js` — history rows carry no inline bytes, only a blob url) and runs the SAME vision call `captionImages()`'s `ref` branch would, through the same content-addressed `cachedVision()` cache — since the role's focus text is part of the cache key, describing the same image under two different roles naturally lands in two different cache entries. **It does not save on its own** — it returns the fresh text, and the picker drops it into the same draft/edit state a hand-typed description goes through, auto-opening that role's textarea so the user reviews (or Cancels) before Save persists it via `onSaveRefImageCaption(entryId, refImageIndex - 1, draft, roleId)` — an AI description is never allowed to silently overwrite a stored one. A failure (no vision model selected, fetch/model error) shows inline as "✗ &lt;message&gt;" under the row/picker it came from, rather than failing silently.

**Storage: a role-keyed map, not a single field.** `refImages[i].captions` is `{ [roleId]: text }` — `App.jsx`'s `saveRefImageCaption(id, imageIndex, text, roleId)` writes `{ ...im, captions: { ...(im.captions || {}), [key]: text } }` where `key = roleId || im.role || ROLE_NONE` (`ROLE_NONE = '_unassigned'`, `src/constants.js` — the map key used when an image has no assigned role at all). This call is **never** told to write the legacy flat `im.caption` field again — that field is frozen wherever its last writer (the original captioning pipeline) left it, and only ever read through `resolveRefCaption`'s own-role fallback. **Pick-time behavior is deliberately unchanged**: dragging/clicking a thumbnail into a new generation still only carries over the image's own-role text (`Tile`'s `onPick`, via `img.caption`) — the alternate-role descriptions are browse/edit-only in this panel for now, not yet selectable at pick time. `HistoryPanel.jsx`'s plain editor calls the same `saveRefImageCaption` with no 4th argument, so it implicitly targets the image's own role — unaffected by the multi-role feature, it just now reads/writes through the map instead of the flat field.

**Gallery-only, not the history card — and a real regression this surfaced (earlier round).** The button was first added to both `ImageInfoPanel` and `HistoryPanel.jsx`'s `RefImageCaptionRow`, then removed from the latter: a finished history card shows an ALREADY-GENERATED prompt, and re-describing a reference there doesn't retroactively rewrite that prompt — it reads as broken, not useful, there. The gallery is different: its whole point is preparing an image to be reused as a reference in a NEW generation, where a fresh/better description directly helps. Chasing this down also caught a real bug behind a "the button just isn't there" report: `consider()`'s `captionScope` was gated on `!im.caption` — a leftover from when `'ref-item'` meant "nothing extracted yet, use the splice fallback." Once an image had been individually saved once, it silently fell OUT of `'ref-item'` scope back to plain `'ref'` — hiding the button, **and** making a second edit on that same image save through the OLD whole-block `onSaveCaption()` path again. `captionScope` must depend only on "is this image's position within its entry known" (`refImageIndex != null`), never on whether it already has text — `test/historyImageGallery.test.jsx` has a dedicated regression case (edit an image once, confirm it's still `'ref-item'` on the next read, edit it again, confirm siblings are still untouched).

Loaded image objects and history-snapshot image fields carry a `hash` field (`imageHash(base64)` from `src/utils.js`) — added in `ImagePanel`/`MinimaxRefPanel` load paths, `pickHistoryImage`, `restore`, and the `runWriter` snapshot. It is threaded through the drag/pick payload so downstream code reuses it (`d.hash || imageHash(d.base64)`); the vision cache does not depend on it (it always re-hashes bytes), so legacy entries without a stored `hash` still work.

Each thumbnail is `draggable`; `onDragStart` calls `setDragImage({url,mediaType,fileName,hash,caption,role,note,captions})` (payload held in `src/imageDrag.js` module scope) and puts only `DRAG_MIME` on the `dataTransfer` — `caption`/`role`/`note`/`captions` are populated only for a `ref`-slot pick (a frame/render pick sends `''`/`null`/`''`/`{}`). `ImagePanel` and `MinimaxRefPanel` both check `hasDragImage(e.dataTransfer)` in their `onDrop` and, if set, call `takeDragImage()` — `ImagePanel` via a no-resize `loadFromData()`, `MinimaxRefPanel` (`refFromData()`) by appending a ref object. Clicking a thumbnail routes through `App.pickHistoryImage(data)`: in MiniMax `ref` mode it appends to `refImages` (cap 6); otherwise it bumps `seeds.{first|mid|last}` (a `{data,nonce}` object) which `ImagePanel`'s `useEffect([seed?.nonce])` picks up and loads — filling the first empty frame in `firstlast` / `firstmidlast`. `seeds` is reset by `switchMode` / `switchTarget`.

**Picking into `ref` mode carries over the image's own role, note, and known descriptions — it used to silently discard all three.** Both `pickHistoryImage` (App.jsx, the click path) and `refFromData` (MinimaxRefPanel.jsx, the native-drag-onto-the-panel path) used to hardcode the new reference's `role` to `MINIMAX_H3_REF_ROLES[0].id` regardless of what the picked image was actually tagged as — a real correctness gap: picking an image previously used as a Location reference could silently default to Subject/Identity, so the NEXT generation would run vision with the wrong role's focus/system prompt on it. Both now default `role: data.role || MINIMAX_H3_REF_ROLES[0].id` and `note: data.note || ''` instead. They also carry `captions` (the picked image's full role → text map, from `HistoryImageGallery`'s `consider()`) onto the new live reference object — **session-only, gallery-derived UI data**, not persisted through `refImagesToSnap`/`refImagesFromSnap` (`src/workspace.js`, which stay on their existing explicit field list) or into history; it exists purely so `MinimaxRefPanel`'s Role `<select>` can mark, per option, whether THIS exact image already has a cached description for that role — `${r.icon} ${r.label}${im.captions?.[r.id] ? ' ✓ described' : ''}` (a native `<select>` can't render rich per-option markup, so the icon and marker are plain text prepended/appended to the label) plus a title tooltip spelling out what a role switch will do. The actual guarantee that generation reuses the right description is the pre-existing content-addressed vision cache (`cachedVision`/`visionCacheKey`, same system/focus text construction in both `captionImages()`'s `ref` branch and `describeRefImage`) — carrying over the correct default `role` is what makes that cache actually hit rather than silently describing the image fresh under the wrong focus.

### Image roles and the per-image record (still-image targets)

**Every image has a role.** `IMAGE_ROLES` (`src/constants.js`) = a new `general` role ("whole image", the default for anything nobody assigned a role — including the legacy `_unassigned` key and every older entry) + the six `MINIMAX_H3_REF_ROLES`. `General` is deliberately **not** in `MINIMAX_H3_REF_ROLES` (H3's dropdowns, subject numbering and vision focus have no "whole image" notion); `normalizeRole()` maps anything unknown/unset to it, and a ref-mode pick receives `null` instead of `general` (`h3RoleOrNull` in `HistoryImageGallery.jsx`) so H3's Role select keeps defaulting.

**One record per image, not per generation.** `server/imageMetaStore.mjs` keeps `{ [imageHash]: { role, captions: { [roleId]: text } } }` (one JSON file, `image-meta.json`; `App.jsx` `imageMeta` state, `patchImageMeta`). This is the image's *current* role and per-role descriptions — history entries and library items still carry their own copy of what a generation used, but nothing reads *them* as the truth any more. The bug this fixed: `collectImages()` used to keep only the **newest** entry that used an image, so a FLUX.2 Klein run (image in the `firstImg` frame slot) replaced the tile and hid the role-keyed descriptions of an older reference-mode entry — which looked like the description being overwritten — and frame tiles had no role UI at all. Now `collectImages(history, imageMeta)` **aggregates across every use** (newest wins per role, not per image; a frame entry's flat `h.caption` is filed under that entry's `firstImg.role`, else General; multi-frame captions belong to no single image) and overlays `imageMeta`, which wins. Tile `role` = record → newest use with an explicit role → General; `caption` = the text under that role. `ImageInfoPanel` shows a Role select, one row per described role and the describe-for-another-role icons on **every** tile that has a content hash (a hash-less old Grok render keeps the flat read-only revised prompt). Edits/describes write `imageMeta[hash].captions[role]`; a ref-item or library tile *also* keeps writing its entry/library record so the History card editor and the gallery never show each other stale. `describeImage(img, roleId)` (App.jsx, via `describeUnderRole`) returns text without saving — same review-then-Save flow as before.

**Role steers the still-image prompt.** The Reference Image card on every image target has a Role select (`ImagePanel` `roleValue`/`onRoleChange`; `imageRoleOf(im)` = `im.role` → record role → General; changing it also patches the record). `captionImages()`'s image branch: description under the current role from `imageMeta[hash].captions[role]` → `firstImg.captions[role]` (pick / restore / queue) → **vision** (General = the target's own vision prompt; any other role = `describeUnderRole`, the same system/focus as H3 ref mode, so the gallery's 🤖 Describe and a generation share cache keys; Pose swaps in `VISION_PROMPT_MINIMAX_H3_POSE`), then the fresh text is written back to the record under that role (never replacing another role's text or an edit — a role with text returns before vision). `buildWriterUserText(… refRole)` (`src/adapt.js`) then labels the reference block with the role and what it may contribute (`IMAGE_ROLES[].imageUse`): *"Reference image — ROLE: Pose / Composition. It contributes ONLY the body pose and framing … do NOT describe anything else from the reference"*; with no typed description it asks the writer to invent a fitting subject/scene and use the reference only for that aspect. `REFERENCE_RULE_IMAGE` (shared by the Klein/flux/krea2turbo/grokimage/zimage system prompts) carries the matching rule. Typed "Image Description" always leads; General keeps the "supporting details only" wording. **Restore / queue**: `imgToSnap`/`imgFromSnap` persist `role` (never the descriptions); `snapshotToWorkspace` attaches the snapshot's own `caption` as `firstImg.captions[role]` for a single-image snapshot (read fresh from the entry each restore, so it can't go stale), and `addToQueue` puts the description under the queued role into the snapshot's `caption` slot — both skip the vision call. The Adapt panel's own builder (`buildAdaptUserText`) is unchanged.

### Copying input images to ComfyUI

Whenever an input image is loaded (any `frameMode`, any image-capable target), a "⇪ Copy to ComfyUI input" button appears next to the image panel(s), alongside a small ComfyUI server URL field. Clicking it calls `uploadImage()` in `src/comfy.js` for each currently-loaded image (reusing the same `currentImages()` helper the ZIP export uses for naming/ordering), which `POST`s each one to ComfyUI's own `/upload/image` endpoint — landing them in ComfyUI's `input/` folder, ready to pick from a `LoadImage` node's dropdown. Like Ollama's `OLLAMA_ORIGINS=*`, this needs ComfyUI started with `--enable-cors-header` for the browser to reach it. This is intentionally minimal — no workflow JSON, no prompt injection, no queueing; it only moves image bytes into ComfyUI's input folder.

### Prompt length control

`PROMPT_LENGTH_OPTIONS` (Concise / Standard / Detailed) in `constants.js` maps to `PROMPT_LENGTH_INJECT` — instruction strings appended to the writer's user message in `runWriter()` as `lengthPart`. Default is `'standard'`. The `concise` key injects nothing (lets the system prompt's native length guidance stand).

### LoRA triggers (standalone workspace)

`src/loras.js` owns the shared LoRA library (`loadLoras`/`saveLoras`, `localStorage['prompt-enhancer-loras']`), one entry per LoRA: `{ id, name, trigger, kind: 'character'|'style', note }`. `LoraPanel` ("LoRA Triggers", shown whenever `targetTakesLoras(target)`) toggles which of them a given generation uses (`activeLoraIds`, per-workspace state — travels with history/queue/adapt like any other input field, via the `WORKSPACE_FIELDS` registry in `src/workspace.js`); `loraInstruction()`/`withLoraTriggers()` tell the writer about the active triggers and repair the finished prompt if one came back missing or mangled.

A `'character'`-kind LoRA's instruction line can optionally name whose trigger it is (`l.subject`, e.g. *"character trigger for Mara — put it immediately before or after the first mention of the character it names"*), which matters once more than one is active at once — otherwise the writer has no way to tell which token belongs to which person in the scene. The Scriptwriter has its own mechanism for this (a character LoRA bound directly to a bible cast member, `c.lora`, `LoraPanel`'s `kinds={['style']}` there so its own chips never show a character LoRA at all); the standalone workspace has no bible, so **`loraSubjects`** (id → typed name, `WORKSPACE_FIELDS` row in `src/workspace.js`, `App.jsx` state `loraSubjects`/`setLoraSubjects`) fills the same role — a small inline text field appears under a `'character'`-kind chip once it's toggled active (`LoraPanel`'s `subjects`/`onSubjectChange` props), and `App.jsx`'s `activeLoras` merges a non-empty typed name onto that LoRA object as `.subject` before it reaches `loraInstruction`/`withLoraTriggers`. `AdaptPanel` needs no extra wiring for this — it receives the already-merged `activeLoras` and spreads the live `workspace` (which already carries `loraSubjects`) into the adapted entry's snapshot.

### Adapt to text-only prompt

`AdaptPanel` ("⇄ Adapt for another model", rendered after the results, gated on `caption || adaptSourceOverride || results.some(r => r.text)`) re-targets a completed — or restored, or history-selected — generation into a text-only prompt for a **different target + model**, and **saves it as a new standard history entry** (`target: destTarget`, `frameMode: 'single'`, no images, `vision: null`, `adaptedFrom: { target, frameMode, ts }`) via `App.saveHistory` — the live workspace / target / `results` are never touched. Two source cases: **image-based** — the vision/image descriptions are folded into the prose (via `foldCaption`) so no reference image is needed; **text-only** — the original produced prompt itself is the source, re-expressed in the new target's format ("text-to-video prompt → text-to-image prompt"), with a `SOURCE PROMPT — written for <label>` block (the "include original prompt" checkbox only appears in the image case; text-only always uses it). The panel has its own destination-target button row (`ADAPT_TARGETS` in `src/adapt.js` = every target except `scriptwriter` / `dramabox`), an independent model `<select>`/`<input>`, and inherited-but-overridable duration (video targets) / aspect ratio (`minimax_h3` only). It calls `callOllama(model, buildAdaptUserText(...), systemPromptFor(dest, 'single'), cfg, cfg.temperature)`.

`src/adapt.js`:
- `foldCaption(caption, sourceFrameMode)` — strips caption scaffolding: `ref`-block `Image N — role: X, preservation: Y (marker): …` → `X: …` (drops the H3-only preservation/marker), `Requested use of this reference:` → inline `(intended use: …)`, `Audio 1 —` line dropped; `firstlast`/`firstmidlast` `FIRST FRAME:` / `CHANGE:` etc. relabelled to `Opening state:` / `What changes over the shot:`; single/prose passes through.
- `buildAdaptUserText({ destTarget, scene, foldedCaption, duration, aspectRatio, stylePart, lengthPart, audio, originalPrompt })` — mirrors the matching text-only branch of `runWriter()`, swapping the frame/ref block for a "Visual details to incorporate (… there is NO reference image …)" block (labelled "Reference image description:" for image targets, so their inert "if a reference-image description is provided…" clause activates).
- `buildStylePart(opts)` — the `stylePart` construction (style + creativity + dialogue + "things to avoid") extracted from `enhance()`; `enhance()` calls it with the real target `type` (byte-identical output), `AdaptPanel` with `forceNonImageWording: true`.

`App.jsx`: the `runWriter` snapshot now stores `caption: frameDescription || null`; `restore()` rehydrates it. Every standard history card with an output shows a `⇄ Adapt` button. `startAdapt(h)` sets `adaptSourceOverride` immediately (cleared by `switchTarget` / `enhance` / `restore`): with a stored `h.caption` it's used directly; with no caption but stored image bytes (`entryHasStoredImages(h)`) it flags `captioning: true` and calls `captionForEntry(h)` — which re-runs the vision step from the entry's stored images via `captionImages(src)` (an optional `src` object overrides the live workspace state) using `h.vision` only if that model is still in the current `models` list, else the current `effectiveVision`; with neither, the panel opens straight away and works from the original prompt text. `cachedVision` takes an optional `model` param for this. `AdaptPanel` disables Generate and shows "👁 Reading the images…" while `captioning`. `LTX_INTRO` / `LTX_GUIDE_INTRO` gained a two-sentence "if NO frame description is given (pure text request)" clause (also fixes the pre-existing bare text-only LTX path).

### SDXL target notes

Unlike FLUX/LTX targets, `sdxl` outputs **two labeled blocks** (`POSITIVE:` and `NEGATIVE:`) of comma-separated Danbooru tags. The writer system prompt enforces strict tag ordering (quality tokens → subject count → character details → pose → setting → composition → lighting → style) and always includes a negative prompt. There is no SD-style weighting syntax — tag order carries the weight signal. `SDXL_RESOLUTIONS` includes the 4:3 pair (1152×896 / 896×1152) not present in `FLUX_RESOLUTIONS`.

### MiniMax H3 target notes

`minimax_h3` compiles to H3's own schema — either three fields (`integrated_multimodal_description` / `overall_soundscape` / `non_diegetic_music`) or, in `Ref2VA`, six fields (`subject_definitions` / `summary` / `retention_analysis` / `detailed_description` / soundscape / music). Frame mode maps to H3 mode: no image = T2VA, one image = I2VA, `last` = L2VA, `firstlast` = FL2VA, `ref` = Ref2VA (up to 6 role-tagged reference images via `MinimaxRefPanel.jsx`, each with a `MINIMAX_H3_REF_ROLES` role, a `MINIMAX_H3_PRESERVE_OPTIONS` preservation marker, and an optional free-text `note` on how to use it). `MinimaxRefPanel` also renders non-blocking amber hints for risky reference sets (wardrobe with no identity ref, ≥2 identity refs, ≥2 "Exact" locks) and up to **two voice-timbre audio references** (`refAudios`, an array — H3's audio input takes two samples, `ref_audio_0`/`ref_audio_1`; each file ≤10 MB) — when present, `captionImages()` appends one `Audio N — voice-timbre reference (marker: reference): …` line per reference and `SYSTEM_PROMPT_MINIMAX_H3`'s Ref2VA block emits a matching `<Audio N>` `subject_definitions` line + a `reference`-marker `retention_analysis` line for each. Entering `ref` mode seeds `h3RatioId` to `port916` (9:16 portrait — the validated Ref2VA short-drama format); the ratio buttons only highlight on a real `h3RatioId` match. `App.jsx` `runWriter()` builds the `MODE:` line, frame/reference block, `Aspect ratio:` line (from `h3RatioId` / `MINIMAX_H3_RESOLUTIONS` for T2VA/Ref2VA; "derived from the input image(s)" otherwise), `Target duration:`, and the soundscape/music sections. The snapshot persists `note` per ref image and `refAudios` (under the unchanged `refAudio` snapshot key — `refAudiosFromSnap`/`refAudiosToSnap` in `src/workspace.js` handle the array; an entry saved before the second slot existed stored one bare object there and is read back as a one-item list), and `restore()` repopulates both. This mirrors the Scriptwriter's own generalization to two voice references per clip — see "Per-clip voice-reference pinning" above; that section's unverified-quality caveat applies here too.

The `.claude/skills/h3-storyboard` skill is the source for the performance and physics rules in `SYSTEM_PROMPT_MINIMAX_H3` (rules 3a, 4, 6, 9–13) — all empirically derived from real H3 output, not docs. Consult it (and its `SOURCES.md` verification table) before revising those rules.

**Dialogue tag format — a deliberate, flagged divergence from a documented empirical finding.** Rule 6/6a's spoken-dialogue format is `[Language] "…"` (language tag immediately before the quoted words) rather than the earlier `<d>[Language] …</d>` wrapper — changed 2026-09-14, user-directed, across `SYSTEM_PROMPT_MINIMAX_H3` (rules 1/6/6a and the Ref2VA dual-label example), `src/manualH3.js`'s seed/legend text, and `src/loras.js`'s LoRA-placement instruction. `.claude/skills/h3-storyboard/SOURCES.md` (`` `<d>` 重新分配鏡頭時間 ``, 2026-08-26) documents a measured H3 generation where the `<d>`-tagged shot claimed extra frames from its neighbors (55→84 of a 74-frame spec) at the cost of background continuity in the following shot — i.e. `<d>` was not purely cosmetic, it had a real effect on H3's internal time-budget allocation. That finding was surfaced to the user before this change; they chose to proceed anyway. The effect is **presumed to still apply** to the new `[Language] "…"` format — nobody has re-run the comparison — so don't treat its removal as having fixed the background-continuity risk; `SOURCES.md`'s revision log (2026-09-14 entry) carries the full caveat and should be updated with real numbers if the new format is ever tested against it.

**Manual mode — write the H3 prompt yourself, zero AI calls.** A **"✍ Write it yourself"** toggle (`manualMode` state, `target === 'minimax_h3'` only) sits inline with the Scene label. When on, the Scene textarea stops being writer-LLM input and becomes the *literal* story text: the user writes their own shot breakdown directly in H3's inline tag syntax (`[Shot N]`, `<Subject N>`, `<Picture N>`, `[Language] "…"` for spoken dialogue, `(Sk)` — the exact tokens the writer LLM is normally taught to emit), and `src/manualH3.js` deterministically assembles it into a schema-correct H3 prompt with **no vision captioning and no writer-LLM call** — `enhance()` short-circuits before the `effectiveWriter`/`effectiveVision` guards. This sits alongside the normal AI pipeline (untouched when the toggle is off), covering all 5 H3 modes (T2VA/I2VA/L2VA/FL2VA/Ref2VA — the four non-Ref2VA ones are 3 flat fields, trivial once Ref2VA's assembly exists).

`src/manualH3.js` is pure (no React, no fetch — same spirit as `workspace.js`/`adapt.js`/`loras.js`, tested the same direct-input/exact-output way in `test/manualH3.test.js`), built strictly against `SYSTEM_PROMPT_MINIMAX_H3`'s own schema:
- `parseShots`/`parseShotLabelUsage`/`parseSubjectSpeakers`/`findMalformedTags` mechanically scan the user's own typed text — since the user writes the tags themselves, "which shot is `<Subject 1>` in" is a lookup, not a judgment call, and a near-miss tag (`[shot 2]`, `<Subject1>`) is reported, never silently auto-corrected.
- `numberSubjects(refImages)` assigns `<Picture N>` by list position and `<Subject M>` only across non-pose-role references (mirrors `SYSTEM_PROMPT_MINIMAX_H3`'s own numbering rule) — Manual mode deliberately **never folds two references into one Subject** the way AI mode occasionally does (that judgment needs a caption/context read this module doesn't have); this is a visible, intentional divergence from AI-mode output.
- `subject_definitions`/`retention_analysis` line builders reuse each reference's own `role`/`preserve`/`note` (captured with zero AI in `MinimaxRefPanel.jsx` already) — `note` doubles as the literal "preserving …" text when present, with a generic per-role fallback phrase when empty; the retention "reason" clause reuses `MINIMAX_H3_PRESERVE_OPTIONS[x].hint` (single source of truth, not a parallel table).
- **Audio→Subject binding is an explicit picker, never positional.** Each `refAudios[i]` carries a `subjectRef` — the **hash** (not the volatile `id`, which is regenerated on history restore — mirrors the Scriptwriter's own `refKey(im) = im.hash` pinning) of the reference image it belongs to, set via a "Voice" `<select>` on the *image's own card* in `MinimaxRefPanel.jsx` (see "Per-reference LoRA and voice binding" below — this used to be a picker on the audio card, gated to Manual mode only; it now lives on the image card and works in both modes). `bindAudioToSubjects()` resolves it; validation blocks an unassigned or dangling `subjectRef`, and blocks an audio bound to a subject that never gets a speaker id (`(Sk)`) in the user's own text.
- `validateManualH3()` blocks assembly (`buildManualH3().ok === false`, surfaced via the normal `globalError` banner) on: zero `[Shot N]` markers anywhere, any malformed tag, an undeclared `<Subject N>`/`<Picture N>` reference, a missing/dangling audio binding, or a blank Soundscape (Manual mode requires it explicitly — type `"silence"` for none; nothing invents it the way AI mode's writer can). It only **warns** (non-blocking, shown under the Scene textarea via `manualWarnings` state) on a declared-but-never-used reference — still gets a line, marked `(not referenced in the text)` — and on non-increasing shot numbers.
- The assembled text still runs through the existing `withLoraTriggers()` repair pass (pure text manipulation, not an AI call — `TARGETS.minimax_h3.loraInject.fields` already targets exactly the field names this module emits) before being saved. The history snapshot's `model` is the sentinel string `'manual'` (`modelProvider()` in `src/history.js` special-cases it to the label "Manual" rather than misreading it as Ollama), `vision: null`.
- Since the user types dialogue directly as `[Language] "…"` and there is no writer LLM left to instruct, `manualUI` (`manualMode && target === 'minimax_h3'`) also hides the now-inert Style/Creativity/Prompt-Length/Avoid/Dialogue/Spoken-Language controls in `App.jsx` while manual mode is on, to avoid the "I set X but it did nothing" confusion a silently-inert control would cause — Duration, Aspect Ratio, Soundscape, Music, the reference panel, and LoRA controls stay visible since the assembler and `withLoraTriggers()` still consume them. The toggle's `onClick` seeds the Scene textarea with real, editable example text the moment it switches on over a blank field — never overwriting anything already typed — so there's something to edit rather than an empty box; it also seeds Soundscape (`'Quiet room tone.'`, same blank-field-only guard) since that field is required in Manual mode and nothing else fills it — without this, the very first "Assemble prompt" click after the toggle failed on a field the user hadn't been asked to touch yet.
- **The seed is built dynamically** by `buildManualSeed(refImages, refAudios)` (`src/manualH3.js`, reuses `numberSubjects()` and `bindAudioToSubjects()`) from the *actual* configured reference set — right count, right roles named (a `wardrobe` ref reads "wearing `<Subject 2>`'s jacket", a `location`/`environment` ref reads "framed against the backdrop from `<Picture 3>`", a `pose_composition` ref is never named), falling back to a plain untagged example with zero non-pose references. **Every audio explicitly bound to a subject (the "Voice" select on that reference's own card) gets its own `[Language] "…"` dialogue line and speaker id (S1, S2…) in the seed** — this is the fix for a reported bug: with 1-2 bound audios and no dialogue line naming their subject, the very first unedited "Assemble" click failed Manual mode's own validation ("Audio N is bound to `<Subject M>`, but your text never gives that subject a speaker id"); the seed now always ships already-valid against that check. The bound subject is whichever reference the audio was actually linked to — not necessarily the "main" identity subject, since a voice can be bound to any subject-bearing reference (wardrobe, product, etc.). With no bound audio, the seed falls back to its old single generic line. A persistent one-line tag legend (`MANUAL_H3_LEGEND_REF`/`_DEFAULT`, still fixed text — it describes syntax, not content) stays under the textarea regardless of what's typed there, since the legend itself must never become literal seeded prose (mode-specific: the `<Subject N>`/`<Picture N>` mention only appears for `ref` mode, the only one with reference images to tag). The placeholder (same seed builder call) is only the fallback for if the field is cleared again.
- `manualMode` and each `refAudios[i].subjectRef` round-trip through history/queue/adapt via `WORKSPACE_FIELDS` in `src/workspace.js` (`manualMode` a plain boolean row; `subjectRef` folded into the existing `refAudiosToSnap`/`refAudiosFromSnap` array functions) — no separate plumbing needed, per that file's own design.

**"✍ Manual Prompt" — a THIRD, independent action, distinct from Manual mode above.** A separate button sits next to "✦ Enhance Prompt" in the generate-button row (`target === 'minimax_h3' && !manualUI` — so it's never shown alongside "✍ Assemble prompt", which the raw-tag Manual mode toggle already covers). Instead of requiring the user to hand-write the whole shot breakdown in H3 tag syntax, one click instantly assembles a full H3-schema draft from whatever the *normal* AI-mode fields already hold — Duration, Aspect Ratio, Soundscape, Music, Dialogue + Spoken Language, the reference panel — with the free descriptive-prose field left as an unmissable placeholder to hand-edit directly in the results textarea, same as any AI output. Still zero AI calls. `App.jsx`'s `buildTemplatePrompt()` calls `buildH3Template()` (`src/manualH3.js`), which:
- Reuses the **existing** `assembleManualH3()` dispatcher for the actual 3-field/6-field schema shape — no new schema-assembly code, no `validateManualH3()` gate (this is a draft, not a final assembly, so it always returns text).
- Builds one placeholder-wrapped body via `buildTemplateBody()`: a leading settings note names aspect ratio, duration, style, and avoid/negative text (none of these are real H3 schema fields, so this note is the only place they appear) plus either the typed Scene text as a starting point or a generic "describe the scene here" cue. In `Ref2VA` mode it reuses `buildSubjectClauseParts(refImages)` — extracted out of `buildManualSeed` (both call it now; `buildManualSeed`'s own output is unchanged) — to weave real `<Subject N>`/`<Picture N>` mentions into the note, so `subject_definitions`/`retention_analysis` show each reference as actually "used," not "not referenced in the text." A typed Dialogue (+ Delivery) field becomes a real `[Language] "…"` line, attributed to whichever subject has a bound voice reference (falling back to the main identity/product subject) with a literal `<Subject M> (S1)` speaker tag — required, not decorative, since `assembleRef2VA` resolves a bound audio's speaker via `parseSubjectSpeakers()` scanning the body text itself.
- **Never uses `[`/`<` brackets in its own scaffolding** — those are live H3 tokens that `parseShots`/`findMalformedTags` actively scan for, and `H3SyntaxBadge` runs on every result automatically, so a bracketed placeholder would misparse as a broken tag on a fresh draft. All scaffolding text uses `«…»` guillemets instead, and there's no trailing placeholder second shot in any mode (one real `[Shot 1]` only).
- Substitutes its own placeholder note for a blank Soundscape (this path has no validation gate requiring it, unlike Manual mode above) instead of emitting an empty `overall_soundscape:` field.
- Ignores Creativity and Prompt Length entirely — both only modulate how an LLM writes, and there is no LLM in this path.

The result is saved to history with the sentinel `model: 'template'` (`modelProvider()` in `src/history.js` labels it "Template" — kept distinct from Manual mode's `'manual'` sentinel so the two are filterable separately). It is **not** wired into the queue system (it's instant — there's nothing to defer) and does not touch `manualMode`/`manualUI` state in either direction.

**"Timeline anchor (Add Guide)" — letting a reference image be a Guide, not just a Reference.** MiniMax H3's real ComfyUI workflow ("Reference-to-Video + chained Add Guide nodes," `minimax-h3-multireference-prompt-spec.md`) distinguishes a plain identity/style/etc. reference from a **Guide**: an image pinned to a specific *second* the composition must pass through. The Scriptwriter already has this (`shot.anchors`, `H3_MULTIFRAME_ADDENDUM` in `constants.js`); the main pipeline gets the single-generation equivalent — a plain field on the reference image itself, `refImages[i].atSeconds`, since there's one shot list here rather than the Scriptwriter's per-clip one. **Deliberately scoped to the manual workflow only** — the normal AI "Enhance Prompt" writer call ignores it entirely, same as before this feature existed; only the two manual actions above change their output for an anchored image.
- `MinimaxRefPanel.jsx` shows one always-visible "Timeline anchor (Add Guide)" number input per reference card (any role, not just Pose/Composition), labelled "ignored by the AI writer" — it's always visible rather than gated on the `manualMode` toggle because the "✍ Manual Prompt" template button (which also consumes it) is only reachable when that toggle is *off*; gating the input on the toggle would hide it exactly when the template needs it.
- **A subject-bearing anchored reference gets a SEPARATE `<Picture N>` line, never a merged sentence** — corrected against `minimax-h3-multireference-prompt-spec.md` §2/§5.3/§8, whose worked example and minimal template both show a dual-role image ("semantic reference" + "concrete frame anchor/storyboard keyframe") as two parallel lines (`<Subject M> is …` unmodified, then `<Picture N> is a storyboard keyframe for the target composition at MM:SS.mmm.` added after), never a single sentence combining both via "It is also …". `assembleRef2VA` appends `buildAnchorDefinitionLine`/`buildAnchorRetentionLine` (new, both `<Picture N>`-keyed) for each anchored, non-Pose/Composition entry, positioned after all the normal per-entry lines — matching the spec's own ordering (every `<Subject M>` line first, then every `<Picture N>` line). The `<Picture N>` retention line's marker still comes from the image's own Preservation setting, but its reason text is the addendum's fixed "target pose, framing, and scene state" wording, not `retentionReason()`'s normal hint — a deliberate tradeoff, not an oversight. A **Pose/Composition** reference has no separate `<Subject M>` line to begin with, so it keeps exactly one line whose wording *switches* (shot-list → anchor phrasing) rather than gaining a second one. `buildSummary()`'s bracketed marker gains a `+ keyframe completion` part whenever anything is anchored. The exported `formatTimestamp()` (MM:SS.mmm) is the single source of truth for this format — `ScriptwriterPanel.jsx` imports it too rather than keeping its own private copy.
- `anchorSentences(refImages)` — one "At MM:SS.mmm, the continuous movement reaches the composition defined by `<Picture N>`." sentence per anchored image, chronologically ordered — is appended to both `buildTemplateBody()`'s Ref2VA branch (the Manual Prompt template) and `buildManualSeed()` (so raw-tag Manual mode's own seed demonstrates the syntax the moment an anchor is configured, since nothing else teaches it in that path).
- `validateManualH3()` (now taking `duration`) and `MinimaxRefPanel.jsx`'s `refWarnings()` both gain the same two non-blocking checks: an anchor outside `[0, duration]`, and two anchors sharing the same time.
- `refImages[i].atSeconds` round-trips through history/queue/adapt via the existing `refImagesToSnap`/`refImagesFromSnap` (`src/workspace.js`), and feeds `H3SyntaxBadge`'s already-generic `anchors` cross-check (`src/h3PromptCheck.js`, built for the Scriptwriter but not Scriptwriter-specific) via `App.jsx`'s `<H3SyntaxBadge>` call.

**Per-reference LoRA and voice binding, and the compose-panel reorder** (both AI mode and Manual mode; MiniMax H3 only). A reference image's card in `MinimaxRefPanel.jsx` carries two more selects, right under Role/Preservation (hidden for a `pose_composition` image, which has no subject to bind either to): **LoRA** (`im.loraId`, a `character`-kind library entry or "— none —") and **Voice** (which uploaded `refAudios[i]` — by writing that audio's own `subjectRef` to this image's `hash` via `setImageVoice()`, clearing any other image's prior claim on the same audio, and this image's prior claim on a different audio — a same-scalar-field swap, no extra bookkeeping). This replaced a design where a voice could only be bound from the *audio* card, and only in Manual mode — normal AI-mode generations had no way at all to say which image a voice belonged to; the audio card now shows a read-only "→ linked to Image N" reflection instead. `App.jsx`'s `activeLoras` is the union of the existing free-chip mechanism (`activeLoraIds`/`loraSubjects` — still the only binding for H3's four non-`ref` frame modes, which have no reference images, and for every other target) and every `refImages[].loraId` set on a card; a structurally-bound LoRA's `subject` (consumed by `loraInstruction()` in `src/loras.js`, writer-LLM text) reads `"the subject in Image N"`. `<LoraPanel>` gets `kinds={['style']}` specifically when `refMode` (H3 + `ref`) is true, since a character LoRA has a real per-image home there instead — every other frame mode/target still sees both kinds, unchanged. In `captionImages()`'s AI-mode `ref` branch, a bound audio's line now names which image it belongs to (`— for the subject in Image N (role)`) instead of leaving the writer to guess from context.

**Each card shows its own resolved `<Subject M>`/`<Picture N>` tag in Manual mode** — `<Picture N>` always matches an image's list position, but `<Subject M>` skips any `pose_composition` image (`numberSubjects()`, `src/manualH3.js`), so "Image 4" is not reliably `<Subject 4>` once a pose reference sits earlier in the list; there was previously no way to look this up other than mental arithmetic, which produced exactly the reported bug (`<Subject 4>` typed for what was actually `<Subject 3>`, failing validation with "no reference image defining it"). `MinimaxRefPanel.jsx` now computes `numberSubjects(images)` itself and shows a small `→ <Subject M> (<Picture N>)` (or, for a pose reference, `→ <Picture N> only — no Subject`) badge next to each card's filename, `manualMode`-only. `validateManualH3()`'s "undeclared `<Subject N>`" error also names the actual subject-bearing count and, when a pose reference is present, explicitly calls out the numbering-skip as the likely cause rather than just reporting "not found."

The whole Frame-Mode-picker + image/reference-input block (`frameModePicker`/`imageInputBlock`, two `const`s computed once in `App.jsx` and rendered at exactly one of two JSX positions depending on `target === 'minimax_h3'`) moved to the **top** of the MiniMax H3 compose panel, immediately after Output/Duration and before Style/Scene/etc. — so a reference image, its role, its LoRA and its voice are all set together, with the free-text scene/prompt fields coming after, not the reverse. Every other target keeps the exact same block at its original (lower) position, byte-identical, since only one of the two render sites ever fires per render — this was chosen over physically relocating the JSX specifically so no other target's markup has to be touched or re-verified.

**Terminology**: the Role dropdown's `environment` entry is labelled **"Location"** (`MINIMAX_H3_REF_ROLES` in `src/constants.js`) — matching the Scriptwriter's own `REF_LINK_TYPES.location` wording for the same concept. Only the display label changed; the `id: 'environment'` (used in saved history, `loraInject`, etc.) is untouched.
